# CellHV OpenStack Discovery Source Audit

**Audit date:** 2026-07-21  
**Evidence tier:** T0 source inspection only  
**Nova revision:** `9d1dd3b8acd2df19d83692e0cade3911c17032b0` (`master`)  
**libvirt revision:** `624f1391ef58f59afdedb42da6635d80504e402b` (`master`)  

This audit narrows the real-lab work required by OSD-001 through OSD-005. It
does not prove that Nova can connect to or manage Cloud Hypervisor and it does
not constitute an OpenStack compatibility claim.

## 1. Actual Nova/libvirt Connection Attempt & First Blocker

- **Connection Attempt:** Nova attempts to connect to `qemu:///system` by default or `ch:///system` if overridden in `nova.conf`.
- **First Blocker (OSD-001):** Configuration validation in `nova/conf/libvirt.py` restricts `virt_type` to `kvm`, `lxc`, `qemu`, `parallels`. Setting `virt_type = ch` causes a configuration failure before any libvirt connection is attempted.
- **Connection URI Override:** If `virt_type=kvm` but `connection_uri=ch:///system`, Nova connects but immediately fails on API calls unsupported by the `ch` driver (e.g., node device enumeration, secret management, or domain capabilities).

## 2. Generated Domain XML

- **Domain XML Generation:** Because Nova configures instances as `qemu` or `kvm`, the generated XML uses `<type arch='x86_64' machine='pc-i440fx-...'>`.
- **Blocker:** Libvirt's `ch` driver rejects this QEMU-specific XML, expecting `machine='ch-...'` and lacking support for many QEMU-specific devices (e.g., `virtio-serial`, `usb-ehci`). No `ch` specific domain XML is generated by Nova natively.

## 3. QEMU-specific Nova Assumptions

- **Hypervisor Defaults:** Nova assumes QEMU capabilities and device types when generating XML (e.g., QMP integration, virtio-net-pci bus addresses, memory backing assumptions).
- **Source References:**
  - `nova/conf/libvirt.py`: Hardcoded list of valid `virt_type`.
  - `nova/virt/libvirt/driver.py`: Hardcoded logic binding capabilities to QEMU features.

## 4. Neutron Expectations

- **VIF Wiring:** Nova's `LibvirtDriver` assumes it can map Neutron VIFs (e.g., tap devices, OVS ports) directly into the domain XML as `<interface>`.
- **Independence:** Cloud Hypervisor handles tap devices directly, but Nova expects libvirt to configure them. The `ch` driver's limited networking support causes mismatches with Nova's VIF plugging logic.

## 5. Cinder Expectations

- **Storage Mapping:** Nova creates block device mappings using QEMU-supported protocols (e.g., iSCSI, Ceph/RBD, local qcow2).
- **Independence:** Cloud Hypervisor supports raw and qcow2, and `vhost-user-blk`. Nova's Cinder attachment logic heavily relies on `qemu-img` and libvirt's QEMU storage translation layer, which is unavailable in the `ch` driver.

## 6. Security and Authority Implications

- **ADR-016 Violation:** The libvirt `ch` driver acts as a stateful authority that starts and monitors the `cloud-hypervisor` process. This competes with `chv-agent`, violating the Core authority boundary.
- **Process Ownership:** Running DevStack and `nova-compute` on a shared host requires libvirt to own the lifecycle, preventing `chv-agent` from being the sole source of truth for the hypervisor.

## 7. Comparison: Generic `ch`, Upstream Changes, and Native Nova Driver

- **Path A (Generic `ch`):** Blocked by Nova's QEMU assumptions and libvirt driver limitations. Fails ADR-016.
- **Path B (Generic Upstream Changes):** Requires massive rewrites to Nova's `LibvirtDriver` to abstract QEMU-isms. Unlikely to be accepted upstream due to the maintenance burden of supporting a non-QEMU libvirt backend. Still fails ADR-016.
- **Path C (Native Nova Driver):** A native CellHV `ComputeDriver` (using `chv-agent` API) avoids libvirt entirely, preserves Core authority, and bounds the maintenance effort to a clean integration layer.

## 8. Effort and Maintenance Estimates

- **Native Driver Effort:** 12-18 engineer-weeks after CellHV Core Phases B-D.
- **Maintenance Cost:** High. Requires maintaining OpenStack packaging, functional test jobs, and adapting to upstream Nova changes.
- **Unsupported Operations:** Migration, resize, snapshot, evacuation, and passthrough behavior will not be supported in the initial native driver.
