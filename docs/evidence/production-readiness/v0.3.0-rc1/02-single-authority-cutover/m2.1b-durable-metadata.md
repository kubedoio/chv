## 1. Baseline and change

- **Baseline SHA:** `39b15393` (`docs(evidence): M2.1a executor-wiring qualification`).
- **PR:** [kubedoio/chv#258](https://github.com/kubedoio/chv/pull/258)
  `m2.1b-operation-metadata` → **merged to main as `297cb904`** (squash, 21 commits).
- **Problem:** the legacy adapter carried audit metadata — requester identity,
  external operation ID, request timestamp, legacy desired generation — only in
  memory (`LegacyMutationIntent`). It was dropped when `SubmitMutation` was built,
  so the durable operation journal could not attribute an operation to its
  requester or client operation id, and an external audit could not reconstruct
  *who asked for what, when, from which generation*. Prompt 02 requires this
  metadata to be **persisted, never memory-only** (the adapter spec flagged
  "constructing an intent alone is not durable audit evidence").

## 2. Change (as merged)

- **Store migration 0004** (`operations` += `requested_by`, `external_operation_id`,
  `request_unix_ms` INTEGER, `legacy_generation` INTEGER, all nullable — additive,
  no data rewrite; registered in the `MIGRATIONS` ledger/checksum/fingerprint
  machinery; applies atomically with 0002/0003 on the multi-step upgrade path).
- **`OperationRequestMetadata`** (new, `cellhv-core-types`): 4 fields + `validate()`
  with input bounds (`requested_by`/`external_operation_id` ≤ 1024 chars,
  `request_unix_ms` in `(0, 253_402_300_799_999]` i.e. year 9999,
  `legacy_generation` in `[1, i64::MAX]`) plus a shared
  `LEGACY_OPERATION_ID_PREFIX = "legacy:"` constant.
- **`SubmitMutation.metadata` / `AcceptOperation.metadata`** are now **mandatory**
  (compile-enforced). `OperationService::submit` validates metadata and rejects
  `legacy:`-origin submissions lacking a generation *before* idempotency
  resolution (fail-closed replay); `accept_operation` writes all four columns in
  the **same transaction** as the operation row (belt-and-braces re-validation +
  a defensive write-path legacy check).
- **Both submit paths journal metadata.**
  - Legacy adapter: real control-plane `requested_by`, `operation_id`,
    `request_unix_ms`, and the parsed `desired_state_version` generation.
  - Native core API: `requested_by = "core-native-v1"`,
    `external_operation_id = <request_id>`, `request_unix_ms` = time Core
    received the request, `legacy_generation = null`.
- **Read-back and integrity gate.** `read_operation_entry` reconstructs
  `OperationJournalEntry.request_metadata: Option<...>` (`/v1/operations` shows
  object | null; the column order vs tuple order is pinned). Every open runs
  `validate_journal_rows` → `enforce_request_metadata_invariants`: columns are
  all-or-nothing; pre-0004 all-NULL rows (incl. `legacy:` ids) are genuine and
  always accepted as `request_metadata: None`; a `legacy:` row with metadata
  present requires a generation; a stray generation with no other metadata is
  corruption. Write-side checks mirror the read rules so no accepted row can ever
  brick a later reopen.
- **Legacy gRPC error contract.** A shared `map_submit_error` maps validation
  `Invalid` → `invalid_argument` in **all five** lifecycle handlers (create/start/
  stop/reboot/delete), so malformed metadata (empty requester, non-positive or
  out-of-range timestamp) yields a proper 4xx, not a 500.

## 3. Invariants (as implemented and reviewed)

1. **Never memory-only.** Both submit paths supply metadata; `SubmitMutation`
   metadata is a mandatory field (cannot be silently omitted).
2. **Atomic durable write.** The operation row and its metadata commit in one
   `Immediate` transaction with the idempotency mapping and first event; a crash
   pre-commit leaves no row; replay reads back the **original** metadata and never
   overwrites it.
3. **Vorward compat / upgrade safety.** A genuine pre-0004 store (any mix of
   `legacy:`/native operation rows, all-NULL metadata) upgrades to v4 and opens
   with `request_metadata: None` for old rows. A failed upgrade rolls back
   atomically: the DB reopens at its prior version and can be repaired then
   re-upgraded (pinned by a regression test).
4. **Read/write symmetry.** The read-side provenance/corruption rules are enforced
   at submit/accept time too, so no conforming write path can produce a row that
   fails reopen (an over-range `legacy_generation` fails accept via checked
   `i64::try_from`, never truncates).
5. **Bounds.** Requester/external-id length, timestamp range, and generation range
   are validated before persistence; the store keeps checked conversions as
   belt-and-braces.

## 7. Remaining risks / honest gaps

- **KVM-VERIFIED unproven.** No real cloud-hypervisor guest lifecycle has been run
  through the wired executor with durable metadata (M2.5 is the scheduled attempt;
  if CH/guest install is not feasible, this stays **unproven** and is reported as
  such). The CI KVM smoke job is label-gated and was `skipping` on this PR.
- **All-NULL blind spot (documented).** A post-0004 row whose metadata columns are
  NULLed by external tooling is indistinguishable from a genuine pre-0004 row; no
  current write path produces it and `PRAGMA integrity_check` catches only physical
  corruption. Stated in `cellhv-core-operation-model.md`.
- **`legacy_generation` on non-legacy rows is a convention, not an enforced rule.**
  Native always journals `null`; nothing forbids a non-`legacy:` row carrying a
  generation. Documented.
- **No wire-level gRPC integration test** asserts the `invalid_argument` status
  end-to-end (the in-process `OperationService`/adapter mapping is tested; the
  agent test harness runs with `core_authority: None`). Future work.
- **M2.2/M2.3 not started:** `CloudHypervisorCoreRuntime` is not yet the single
  full-side-effect effector; the legacy `Reconciler` provider-mutation paths are
  not yet gated off in core modes; NodeCache is not yet a rebuilt projection.
  Single-host = MULTI-HOST/FIELD unproven.
