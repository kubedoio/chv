## 2. Objective (plan.md M2.5)

Install the pinned cloud-hypervisor (v43.0) and a minimal guest on the
qualification host (`/dev/kvm` present), then run **Create / Start / Stop /
Reboot / Delete plus a crash/restart replay scenario through the exact
candidate path**, capturing evidence. If the installation were infeasible,
KVM-VERIFIED would be reported unproven with the exact gap (it was feasible).

"The exact candidate path" is the production single-authority configuration
this campaign built, as defined by the plan's architecture map: the agent in
**`authority_mode = "core-managed"`** — the `AgentServer` routes all five
lifecycle gRPC calls through the **Core authority** (Core journal/executor is
the single durable authority and the single provider effector; the Reconciler
is observe-only; NodeCache is a projection rebuilt from Core execution) —
with real TLS/mTLS, real bootstrap-token enrollment, no
`CHV_ALLOW_INSECURE` anywhere, and every lifecycle command issued through
`chvctl` → BFF → control-plane (orchestrator) → agent gRPC → Core →
cloud-hypervisor v43.0. `core-native` (Core + native HTTP API only, no
legacy surface) is the future end-state mode, but the control-plane cannot
deliver operations to a core-native agent today (it has no gRPC surface and
never enrolls), so it is not deployable as the candidate path yet — the
harness initially targeted it and the correction is recorded here.

## 4. Harness

`/tmp/opencode/m25/kvm-lifecycle-qual.sh` (host-local; quoted in full in the
transcript header comment). Modeled on `scripts/integration/kvm-smoke.sh`'s
proven deployment shape with the candidate-path deviations above. It:

1. Preflight (root, `/dev/kvm`, pinned CH version check, firmware/image
   presence, repo SHA + ahead-of-main diff, binary staging).
2. Generates certs, one-time bootstrap token, admin (bcrypt) and configs;
   the agent runtime dir is created mode `0700` — the Core-authority
   startup validation (`cellhv-core-startup::validate_paths`) requires an
   owner-owned `0700`/`0750` runtime dir, which the production install
   satisfies via `install -d -m 0750` (install.sh:220) and the harness
   mirrors (`chmod 0700`). Legacy-mode harnesses (kvm-smoke.sh) are
   unaffected — `validate_paths` runs only on the Core-authority paths.
2. Generates certs, one-time bootstrap token, admin (bcrypt) and configs.
3. Starts the control-plane, seeds the admin user and the one-time bootstrap
   token (before the agent starts — the agent enrolls at startup and the
   control-plane validates the token against its fresh DB), then starts
   stord/nwd (the agent's DaemonSupervisor adopts them via socket liveness
   probes) and the agent; verifies enrollment issued the node certificate
   and the core API socket is up.
4. Waits for TenantReady, creates the default network, imports the image.
5. `chvctl vm create` (asserting `--cpu 2`/`--memory 1G` land in the spec) →
   `vm start` → asserts Running, one cloud-hypervisor process, and **guest
   boot evidence in `console.log`** (kernel banner + systemd target/login).
6. `chvctl vm reboot` (the PR #274 fix) → asserts a fresh kernel boot in the
   appended console log and the same CH process (guest-level reset).
7. `chvctl vm stop` → asserts Stopped and CH exit.
8. **S1 replay:** SIGKILL the agent while the VM is Running (no in-flight
   op); asserts CH survived the crash, then after agent restart: TenantReady,
   VM converged to Running, exactly ONE cloud-hypervisor process (no
   duplicate VMM), original instance preserved or honestly reported.
9. **S2 replay:** issue `vm stop`, SIGKILL the agent ~1.5 s later (in-flight
   operation); after restart, inspects `/v1/operations` for the interrupted
   op (`status=running` + `recovery_assessment` = the documented
   InspectRequired surface), resolves it through the documented node-local
   `ResolveInspectRequiredOperation` RPC with a factually-derived
   disposition, and asserts convergence to Stopped with no CH process and VM
   resources preserved (stop must not delete).
10. `chvctl vm delete` → asserts absence and CH exit.
11. Collects artifacts (transcript, service logs, console log, core.db dump,
    `/v1/operations` snapshots at each stage, process/bridge state) and tears
    down the services, keeping the test dir.

**Freeze root cause (experiments e8/e9 + CH v43 source analysis, 2026-09-29) — the serial-client-death mechanism, confirmed end-to-end.** e9 (`/tmp/opencode/m25/e9-kill-reader.py`) made the serial client's death the only variable, with marker-triggered kill arms against the full harness recipe (fresh CH, root + seed + tap, live reader from spawn): a **mid-burst kill** (at the `Linux version` banner) freezes the guest deterministically — console stops, no logind, the +60 s press received but unhandled, CH still Running at +120 s, both vCPUs parked in `kvm_vcpu_block` with only timer blips, zero journal entries (e6's exact signature); a **quiet-window kill** (wait-online marker +1.5 s ≈ kernel+5.1, socket queue empty) leaves the guest fully alive — it boots to completion invisibly (console output dropped, disk writes continue — 4.2 MB at +12 s — no console bytes) and the +60 s press yields a clean poweroff, **CH exit 0**. The ch.log discriminator matches: the quiet kill logs `Remote end closed serial socket` (the manager survived; its KILL_EVENT appears at teardown, 62.8 s), while the mid-burst kill produces *no serial-manager lines at all* (silent thread death).

The mechanism is a three-defect chain in the CH v43 source (`vmm/src/serial_manager.rs`, `devices/src/legacy/serial.rs`):
1. **The serial-manager thread dies silently on a client reset.** A client death with unread data in its receive queue is an abortive close (the kernel resets the connection): the manager's `read()` returns `ECONNRESET`, `Error::ReadInput` propagates via `?` out of the epoll loop — and the thread wrapper, `catch_unwind(...).map_err(|_| error!("serial-manager thread panicked")…)`, fires only on *panics*; a normal `Err` return is discarded silently. No log, no `set_out(None)`, no exit event. (This is why e6's and e9-kernel's ch.logs contain no serial-manager lines whatsoever.)
2. **The UART write-error path skips the THR-empty interrupt.** With `out` still pointing at the dead socket, every guest console byte does `out.write_all(&[v])?` → `EPIPE`; the `?` returns early from `handle_write` **before `self.thr_empty()`**, so the transmit-holding-register-empty interrupt is never raised. (The error itself is harmlessly discarded by `BusDevice::write`'s `.ok()` — it is the skipped `thr_empty()` that matters.)
3. **The guest's 8250 tty tx path starves.** Kernel printk on ttyS0 is polling-based and immune — the kernel keeps running, which is why `vm.info` stays Running and the vCPUs merely halt. But `/dev/console` tty writes are interrupt-driven: without THRE the TX circ buffer (~4 KiB) never drains, and once it fills, **PID 1 blocks on a status-message write** — logind never starts, daemons already started keep journalling briefly (networkd to kernel+5.33 and fsckd's kernel+32.4 gasp in 8e boot 3 — both were already running when PID 1 blocked), ACPI presses are received by the kernel but have no consumer, and the vCPUs sit halted with occasional timer blips.

This explains every prior observation: boot 3's journal ending at IPv6LL/kernel+5.33 with its console ending at `Starting systemd-networkd-wait-onl…` (the gen-2 relay died at the boundary with the `OK Finished` line in flight — the console had been quiet since kernel+3.6, so its last captured line simply predates the death); e6's zero journal entries (kill at kernel+0.0008 → PID 1 blocked ~kernel+2, before journald's persistent flush — the 368 KiB of writes at wall+8 in the e9-kernel replication are the rootfs mount, not journal); e6's client B receiving 0 bytes and ECONNRESET only at teardown (the dead manager never calls `accept()` — B sat in the listen backlog); 8e's healthy gen-1→gen-2 capture resume (gen-1's death landed in a quiet window — a clean EOF the manager survived, hence the reconnect was accepted); and every healthy run (live reader throughout). It also inverts the framing: the frozen boots are not a property of the VM config or the platform — they are chv's *own crash-replay* (the S1/S2 agent kills) interacting with a CH defect, landing exactly when console output is flowing.

The corrected press-regime map (superseding 8d's): pre-logind presses are lost (e2/a2); logind+1 s honored, orderly ~32 s (b2/e4); mid-boot +33 s honored, 9.5 s (e5); deep stall ≥+120 s forced poweroff ~1 s (e2/e3/run 7); the 8d/8e "respawned boot ignores presses" rows were **frozen guests, not a regime**. - **Dead-manager detection (implemented — PR #299, squash-merged as main

  agent-log-only, not journaled operations (the adoption-not-journaled

  (`recovery_resolution_event_backfill`) deterministically repairs
  already-corrupted stores — the missing event's content is fully
  derived from its assessment row, idempotent, sequence-contiguous;
  verified against run 10's actual `core.db`. Known caveat on repaired
  stores: backfilled events append at the journal tail, so a
  resolution's recovery event sequences *after* its terminal event (no
  consumer depends on that order; the fixed writer orders them
  recovery-then-terminal).
- **Resolve-as-failed → convergence auto-start race (open, design
  observation; run 10 §5, first realization).** Resolving an
  interrupted stop as `failed` reverts the authority's desired state to
  Running; any reconciler start accepted in the resolve→retry window
  then executes the moment the retry stop's force kill releases the op
  lock (run 10: `StartVm-359dfde9`, 50 ms after the force kill,
  re-spawning the VMM). The system converges and both ops succeed —
  last-accepted-intent wins at the authority — but the observable
  behavior (guest re-appearing seconds after a successful stop) will
  surprise an operator. Options if this is deemed worth smoothing:
  execution-time desired-state revalidation (drop a queued start whose
  desired state was since superseded), or resolve-time disposition
  semantics that keep desired=Stopped until the operator's next intent.
  Not a defect as-built; recorded so the behavior is documented
  expectation rather than mystery. The harness's S2-retry gate now
  checks the op-level contract and records the end state either way.
- **Agent-death vs control-plane state (harness blind spot, fixed in the
  run-10b harness).** A dead agent's node/VM state gates pass against
  stale CP caches (run 10's 9b: TenantReady and Running PASSes against a
  process that died 5 ms after startup). The harness now gates on agent
  process liveness after every 9b restart before any state gate; a
  production-side corollary is recorded in §8 (the CP's cached state has
  no fast agent-death signal — node heartbeat freshness is the
  RELEASED-tier question).
- **Adoption is not journaled (open, LOW).** `adopt_running_vms` mutates
  the runtime map without an operation-journal entry, so the audit trail
  has no record of the re-derivation (only the agent log does). The
  Core executor's op model has no vocabulary for a startup-time
  read-only derivation; adding one (or an agent-startup journal event)
  is the follow-up.
- **Reconciler drop paths discard structured reasons (open, LOW).** The
  legacy reconcile loop's early returns keep rich failure context in
  `record_failure` but the paths that return without recording (or
  record only `e.to_string()`) lose the structured reason fields —
  grep-level audit found no correctness impact, only observability.
- **Serial transport re-derivation trusts `serial.sock` existence
  (open, LOW).** Adoption and re-adoption classify the console transport
  by whether the socket file exists; a Socket-transport VM whose socket
  was cleaned (unclean first bind never materialized, external removal)
  mis-derives as Pty — a retryable start failure via the Pty path, not a
  silent console loss. Persisting the transport choice in the creation
  payload is the follow-up.
- **Untracked-VMM scan returns the first match (open, LOW).** The
  `/proc` scan for a live VMM owning an api socket detects no
  multi-owner conflict; in a pathological split-brain layout it can
  adopt a peer's VMM. Pre-existing class of limitation (the adopted-pid
  probe has the same shape); an flock on the runtime root (the
  recorded split-brain follow-up) is the systemic fix.
- **Union-review gaps (fixed in PR #297, squash-merged `bc9e26a8`).**
  A review of the *cumulative* remediation diff (the three PRs above,
  each reviewed individually) found two cross-PR interactions the
  per-PR reviews could not cover: (1) `readopt_stopped_vm` (#294) never
  consulted #292's `console_draining` latch — a start racing graceful
  agent shutdown could insert a fresh serial connection *after* the
  drain's passes, which process exit would abortively close (the v43
  freeze hazard); readopt now checks the latch pre-connect and
  post-lock, abandoning any fresh connection and failing the start
  with a retryable error. (2) the legacy reconciler's two recovery
  arms swallowed the #294 delete gate's fail-closed refusal
  (warn-and-continue) and re-created anyway — potentially forking a
  second VMM onto a disk a live unreapable owner still holds; both
  arms now fail closed on anything but NotFound. The same PR made the
  stand-in VMM test processes RAII-owned (no leak on panic), routed
  every production console.log site through the shared
  `vm_console_log` helper, and refreshed the stale
  `GRACEFUL_STOP_WINDOW` history note.
- **Local test-suite caveat (qualification host).** `cargo test -p
  chv-agent-runtime-ch` fails 13 `linux_observation`/adoption tests on
  this host against CLEAN main `4d985d4c` (A/B verified with a stash)
  while CI runs the same suite green — the failures are environmental
  to this box, cause unidentified. Local runs of that suite are not
  trustworthy here; CI remains the arbiter (and did verify PR #290).
  Same class, added 2026-09-29: `chv-agent-core` fails 6 `cache` tests
  locally on clean main, and `ch_api`'s
  `connected_probe_enforces_total_deadline_against_trickle_peer`
  (a 60 ms-margin timing test) flakes ~1-in-4 under full-suite
  parallel load while passing in isolation — both clean on CI.
- **Adoption identity hardening.** The adoption scan's process identity is
  `ch.pid` + cmdline + `/proc/<pid>/exe` cross-check (the exe check landed
  with #286's review round) — robust against pid recycling and argv
  spoofing, but weaker than the stub's aspirational pidfd / boot-id /
  cgroup checks. Harden with pidfd and `/proc/<pid>/stat` start-time
  before trusting an adopted pid for anything beyond today's
  kill-refusal semantics.
- **Legacy-mode reconcile convergence with adopted VMs.** #286 makes
  create *refuse* over an adopted-live VM (the double-VMM safety
  boundary), so after an agent restart in Legacy authority mode the
  reconciler's create pass fails cleanly instead of converging: the VM
  runs and lifecycle ops work, but desired-state reconciliation for it
  errors until the VM is stopped. Fix by seeding the legacy runtime
  cache from adoption (or making the reconciler adoption-aware).
- **Split-brain agents on one runtime root.** Adoption refuses to
  overwrite tracked entries and kills are identity-guarded, but two
  agents sharing `{runtime_root}` can both re-spawn a stopped VM.
  Operator-error territory; an flock on the runtime root would make it
  fail loudly.
- **Broadcaster supersede residual.** #286's `same_channel` check makes
  a superseded console broadcaster exit before delivering any bytes,
  but its reconnect can still kick the fresh broadcaster's connection
  once (CH drops the older client on accept) before exiting — a
  sub-second, self-healing flap in a narrow timing window. A full fix
  needs an abort handle on the broadcaster task.
- **Idempotent create-replay.** An executor replay of a create whose
  ack was lost now fails fast ("already running") instead of forking
  the VM, but true idempotence (detect "already created at CH with
  matching config" → report success) remains unbuilt.
- **Pty-transport console across reboot and adoption.** Pty VMs (explicit
  tuning only) lose console capture at reboot (new pty at a different
  path; needs a `vm.info` re-query) and are adopted lifecycle-only.
- **`vm.reboot` non-2xx still reports success** (warn-only, pre-existing):
  callers cannot distinguish a failed reboot from a succeeded one (from
  PR #284's review; changing it alters observable semantics — separate PR).

## 8. Remaining risks / limitations

- **Single host.** One node, one VM, one bridge; MULTI-HOST-VERIFIED and
  FIELD-QUALIFIED remain unproven (they require a second host / real
  deployment).
- **Throwaway deployment shape.** Daemons run from the repo's release
  binaries in a temp dir as root (kvm-smoke.sh's shape), not the packaged
  systemd/user-separated production install (install.sh). The candidate path
  (code, authority mode, TLS posture, enrollment) is production-shaped; the
  process supervision is not.
- **Guest networking is bridge-local** (no upstream NAT): guest boot and
  cloud-init were verified via the serial console; outbound guest networking
  was not qualified.
- **One replay scenario per class** (idle crash, mid-stop crash), not the
  full M2.4 five-window matrix against real KVM; the deterministic
  fault-point machinery is mock-adapter-only.

- **The guest-platform freeze (post-run discovery, root-caused: CH v43
  serial-console defect).** Every frozen boot in the qualification (runs
  8b–8e boots 3, e6, e9-kernel) is attributed to chv's crash-replay killing
  the console relay with console data in flight, hitting the CH defect
  chain (§5 run 8e / e8 / e9, §6): the serial manager dies silently, the
  THR-empty interrupt is skipped, and PID 1 blocks on a `/dev/console`
  write. The S2 stops converged through the force fallback, and the
  harness's old guest-health gates passed frozen boots (the logind gate
  now catches them). Plain `vm start` boots healthily (e8) — the PASS rows
  for "guest kernel booted" / "guest userspace reached" describe real
  boots, not frozen ones, on the non-replay path. No RELEASED-tier claim
  until chv ships a CH build with the upstream main serial rework (in no
  release through v53.0) or completes the chv-side mitigations — the
  drain-before-close half landed (PR #292, CI-VERIFIED; KVM re-qualified
  by run 9, which reproduced the crash-path freeze the drain cannot
  prevent and verified the machinery absorbs it), and the
  guest-liveness watchdog landed as PR #299 and is KVM-VERIFIED
  (run 10b, §5: the crash-path freeze was detected, rebooted, and its
  capture restored in-stack) — the chv-side remediation is complete;
  the upstream CH fix remains the real cure and the RELEASED-tier
  gate.
- **Serial-client-death behavior: proven, and it is the root cause**
  (supersedes the earlier "unproven, secondary" item): a mid-burst
  serial-client death (ECONNRESET, not clean EOF) silently kills CH v43's
  serial-manager thread and freezes the guest (e9-kernel, deterministic);
  a clean disconnect is handled correctly and the guest stays healthy
  (e9-quiet: CH exit 0, `Remote end closed serial socket` logged). The
  adoption's capture-resume after a clean client death is proven working
  (8e's gen-2 systemd lines) and *requires* the prior death to have been
  clean — after a mid-burst death the manager is gone and a reconnecting
  client silently queues in the listen backlog (e6's client B: 0 bytes,
  ECONNRESET only at teardown).
- **Version strings can attest provenance again** — the stale-build-commit
  issue (§6) was fixed in PR #293 (build.rs re-runs on the git state; CI
  asserts the embedded sha equals HEAD). The run-8e binaries predate the
  fix and self-report four commits stale; runs after #293 do not.
- **Control-plane state has no fast agent-death signal (run 10).** With
  the agent dead, the CP's cached node/VM state keeps answering queries
  (run 10's 9b gates passed TenantReady/Running against a process that
  had died 5 ms after startup) — the harness now gates on agent-process

  window until node-heartbeat freshness becomes part of the API

  actions, `reboot_vm` non-2xx Ok semantics, pid-recycling residual)
  stand.
