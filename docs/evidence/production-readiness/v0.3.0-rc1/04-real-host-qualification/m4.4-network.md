# M4.4 — Network Qualification on Real KVM (Nested)

Milestone: prompt-04 M4.4 (plan §"M4.4 — Network qualification").
Candidate: `baa20c0e` (rc1 boundary; frozen — product fixes land post-rc1 on
main, the qualification harness works around candidate defects and records
them).
Host: the qualification host, itself a KVM guest (`systemd-detect-virt:
kvm`) — all guest virtualization is nested virtualization through
`/dev/kvm`. 16 vCPU / 31 GiB RAM. nftables 1.0.9, iproute2, dnsmasq 2.90,
genisoimage 1.1.11.

## 1. Scope

Two evidence tracks, per plan §M4.4:

1. **Prompt-01's privileged host-safety suite, rebuilt as a committed
   script** (`scripts/integration/qual/host-safety.sh`): the two `#[ignore]d`
   root-gated integration tests in `crates/chv-nwd-core/tests/host_safety.rs`
   (`confines_policy_to_chv_owned_traffic`,
   `exposure_survives_firewall_apply`), built from this tree with a candidate
   identity guard (`crates/chv-nwd-core` verified byte-identical between
   `baa20c0e` and HEAD), run as root against real nftables, with the
   nftables ruleset dump persisted for evidence.
2. **The guest network path** (`scripts/integration/qual/m4.4-network.sh`,
   run via `deploy.sh --exec`): attach → connectivity → policy attempt →
   nwd hard-kill/restart/reconcile → stop/start (detach cycle) → second
   network (fallback-CIDR collision) → cleanup, with forbidden-outcome
   assertions on the host stack (links, nft tables, dnsmasq, routes; the
   deploy teardown enforces the final no-residue gate).

Non-scope (inherited from prompt 01, restated): coexistence with
Kubernetes/CNI, Docker-forwarded traffic, or other bridge-owning network
stacks is **not claimed**. Single node; single bridge family
(`chvbr0` / `br-<network_id>`); no VXLAN/fabric (the nwd fabric provider is
disabled in the qual config and fails closed — the agent logs a benign
30 s-cadence WARN about it). Policy *enforcement* end-to-end is not claimed
(see finding N2) — policy behavior is proven at the nwd layer by track 1.

## 2. Harness

New committed scripts (this milestone):

- `scripts/integration/qual/host-safety.sh` — the prompt-01 procedure
  (build → locate the ignored test binary → sudo-run → capture
  `HOST_SAFETY_DUMP_PATH`) with a candidate-identity guard and its own
  leak assertions (no leftover links/namespaces/nft tables).
- `scripts/integration/qual/m4.4-network.sh` — the six-leg scenario below.

Harness changes:

- `env-preflight.sh`: ensure `dnsmasq` + `genisoimage` (product-declared
  runtime deps, installed by `install.sh` but not previously by the qual
  preflight) and stop+mask the system `dnsmasq` unit (the nwd-spawned
  instances are DHCP-only, `port=0`; a system resolver on :53 would
  conflict with systemd-resolved).
- `deploy.sh` teardown: kill nwd-spawned dnsmasq instances (scoped by
  their `/run/chv/nwd/dnsmasq-*` conf path) and remove the runtime dir
  when this deployment created it; scoped `chv-nwd` kill safety net
  (the agent supervisor's replacement instance is a child the PID
  overrides cannot reach if a restart races the scenario's last
  `pids.current` update); `disown` the daemon jobs so scenario SIGKILLs
  don't print bash job-control notices into the evidence log.

Environment note: the candidate hardcodes the dnsmasq runtime dir to
`/run/chv/nwd` (chv-nwd-core `dhcp.rs`/`dns.rs`/`executor.rs`), independent
of `nwd.toml`'s `runtime_dir` — a single-host-path assumption, recorded
here; the teardown restores it only when it created it.

  `nft table inet chv-default` present. Guest: cloud-init NoCloud seed on

  (BFF responsive, non-CHV nft tables unchanged, guest reachable).
- **Leg C — nwd hard-kill → supervisor restart → reconcile:** SIGKILL nwd
  → data plane unaffected (guest pings with nwd dead — bridge/tap/dnsmasq
  are kernel state), the agent supervisor restarts nwd within one ~30 s
  reconcile tick (new pid, api socket live), guest connectivity intact, a
  **new** VM attaches to the existing network (idempotent topology

- **Leg D — stop/start (detach cycle):** graceful stop → CH exits, the

  persist, stopped guest unreachable; re-start → **same deterministic tap

  routing while forced `ping -I br-m44x` works; guest-1 (first bridge)

## 4. Findings

### Pre-run experiments (Phase 0, hold-mode deploy)

The scenario was designed from a hold-mode experiment on the same host
(same candidate, same image): every leg's expected host-state shape was
observed manually before being asserted by the scenario. Notable
observations beyond the scenario's scope:

- The BFF `network create` is DB-only: no host materialization until a VM
  attaches (benign — the VM path materializes on demand).
- The agent **supervises** nwd: an external nwd that dies is replaced
  within one reconcile tick (config under the agent's dir).
- A second nwd instance can hijack the api socket path (unlink-rebind),
  leaving the supervisor's instance live-but-unreachable; the supervisor's
  health check is process-based and does not probe the socket path, so
  that state does not self-heal. Observed only via deliberate manual
  interference (starting a duplicate daemon); not reachable through the
  product's own paths in this topology. Recorded as an observation, no
  issue (single-node disposable host; both processes are root).
- The supervised nwd logs to /dev/null (stdout/stderr of the supervisor's
  child) — nwd log lines only exist for the deploy-started instance until
  its first replacement. The scenario therefore asserts host state, not
  nwd log lines.
- Without dnsmasq/genisoimage installed, the guest degrades silently to
  network-less (warn-only in the agent; no operator-visible error) — the
  preflight change closes this for the qual host; the product-side
  fail-open is folded into the N2 issue's context (no separate issue:
  the tools are product-declared package deps, present on any
  install.sh-provisioned host).

### Product defects (issues filed; candidate unchanged)

All four were demonstrated by the Phase-0 experiment and re-demonstrated
by the scenario runs; the harness records them and works around them:

- **N1 — `vm create --network <name>` ignores the operator-created
  network** (name↔network_id split; implicit fallback network with the
  hard-coded 10.200.0.0/24 CIDR; same-subnet bridge collision breaks
  host→guest routing for the second network). #339 defect class.
  **Issue #354.** Workaround: positive legs use the default network
  (fallback CIDR == deploy CIDR); the collision is demonstrated as a
  recorded outcome.
- **N2 — no operator-reachable network policy path** (BFF update is
  DB-only; the CP never pushes network desired state; the agent RPC is
  unimplemented in core-managed mode; the deployed nft table is bare —
  no default-deny engaged). **Issue #355.** Policy allow/deny is proven
  at the nwd layer by the host-safety suite instead; the end-to-end
  policy claim is explicitly **not** made.
- **N4 — `vm delete` leaves orphaned nic rows that permanently block
  `network delete`** (409 "N VM(s) still attached" with all VMs deleted;
  the count query has no VM-existence check). **Issue #356** (with N5).
  Workaround: documented operator escape (drop the orphaned rows).
- **N5 — `network delete` performs no host teardown** (DB-only delete:
  bridge, nft table, dnsmasq and `/run/chv/nwd` configs persist; the
  stale bridge keeps its subnet route). **Issue #356** (with N4).
  Workaround: the deploy teardown's scoped fallbacks are the actual
  cleanup.

## 5. Residual risk / not claimed

- **Policy enforcement end-to-end is not claimed** (N2): the
  operator-stored `firewall_rules` are dead configuration in the candidate
  and the deployed path installs no policy chains at all. Host safety
  holds trivially on the deployed path (nothing is installed outside
  CHV-owned tables); guest-boundary default-deny is proven only at the
  nwd layer (host-safety suite).
- **Coexistence is not claimed**: K8s/CNI, Docker-forwarded traffic,
  multi-bridge — restated from prompt 01. The qual host runs none of
  them.
- **Two networks on the (fallback) same subnet break host→guest routing
  for the second** (N1): single-network operation is what's qualified.
- **Single node**: no multi-node network semantics (stretched L2/VXLAN
  fabric) exercised — the fabric provider fails closed in this config.
- **Nested virtualization**: all guest networking is nested-virt; absolute
  latency numbers carry that caveat (RTT ~0.2–0.4 ms host→guest).
- The dnsmasq runtime path is hardcoded to `/run/chv/nwd` — a second CHV
  nwd instance on the same host would collide (single-host assumption).
- The supervisor's nwd health check is process-liveness-based; a
  live-but-unreachable nwd (stale socket path) does not self-heal
  (observation above; requires deliberate same-uid interference to
  reach).
