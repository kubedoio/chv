# M4.3 — Lifecycle & Recovery on Real KVM (Nested)

Milestone: prompt-04 M4.3 (plan §"M4.3 — Lifecycle & recovery on real KVM").
Candidate: `baa20c0e` (rc1 boundary; unchanged from M4.1/M4.2 — fixes land on
main, the candidate is frozen).
Host: the qualification host, itself a KVM guest (`systemd-detect-virt:
kvm`) — **all guest virtualization in this milestone is nested
virtualization** through `/dev/kvm`, explicitly confirmed enabled for this
campaign. 16 vCPU / 31 GiB RAM.

## 1. Scope

Via `chvctl → BFF → control-plane → agent gRPC → CellHV Core → CH v43.0`
on this host, single guest (`qual-vm-1`, 2 vCPU / 1 GiB, firmware boot,
default network):

- **Leg A** — create → start → guest-boot evidence (console.log kernel
  banner + logind) → reboot (guest-level, same CH process) → stop
  (graceful) → start (re-spawn path);
- **Leg B** — S1 replay: agent SIGKILL while Running (CH survives,
  convergence, exactly one CH process, no duplicate state);
- **Leg C** — control-plane restart while Running (VM unaffected,
  reconnect);
- **Leg D** — management-plane outage/reconnect (60 s BFF/API unavailable
  window, deterministic operation history after);
- **Leg E** — full stack restart (all four daemons, cold reconcile) — the
  provable subset of host-reboot recovery, labeled as such;
- **Leg F** — stop (graceful, logind-gated) → delete → absence;
- identity + operation-history determinism asserted at every leg (VM
  id/name/node constant, exactly one VM, core.db operations/events counts
  and the BFF task list stable across every restart leg).

Non-scope: multi-node migration (M4.6+), network policy qualification
(M4.4), storage profiles (M4.5), host reboot itself (recorded as
not-provable on this topology; Leg E is the labeled subset — plan §6).

## 2. Harness

New committed scripts (this milestone):

- `scripts/integration/qual/patch-guest-image.sh` — builds the bootable
  qualification guest image. The stock noble cloud image cannot boot
  through the shim → rust-hypervisor-fw chain (GRUB passes
  `root=LABEL=cloudimg-rootfs`; LABEL resolution needs the initramfs the
  firmware chain never delivers — root-caused in M2.5). The patch
  (grub.cfg on the image's BOOT partition: `root=/dev/vda1`, initrd lines
  removed — the noble kernel has VIRTIO_BLK/EXT4 built in) is
  qualification scaffolding, not product; direct-kernel boot of stock
  cloud images remains a recorded follow-up limitation. The script also
  guards the M2.5-documented ESP-label gotcha (`/boot/efi` remounted from
  the loop image's UEFI-labeled ESP — original source recorded and
  verified after detach).
- `scripts/integration/qual/m4.3-lifecycle.sh` — the scenario script, run
  via `deploy.sh --exec` against the candidate deployment (M4.1 shape:
  real mTLS, core-managed authority, one-time bootstrap token, no
  CHV_ALLOW_INSECURE). Timing knowledge inherited from M2.5: logind gate
  before every ACPI stop (pre-logind presses are silently lost), the
  ~32 s snapd stop inside the agent's 60 s graceful window, reboot =
  guest-level reset with the serial rotation captured. All timeouts
  carry nested-virtualization margin (kernel banner 420 s vs the M2.5
  300 s budget).
- `deploy.sh` gained the `pids.current` hand-off: scenario scripts that
  restart daemons record the current PIDs in the test dir, and teardown
  re-reads them (the `--exec` child cannot propagate restarted PIDs back
  to the parent). Also fixed a pre-existing exit-status bug found while
  building on it: a duplicated `SCENARIO_RC=0` reset the
  deployment-error gate, so a deployment with assertion errors could
  exit 0 if the scenario itself exited 0.

Operation-history determinism fingerprint: core.db `operations` and
`events` row counts (read-only URI) + sha256 of the BFF `task list` JSON,
snapshotted after every leg and compared across each restart leg.

## 3. Results

Six runs total; runs 1–5 are documented as findings in §4 (each ended
in a root-caused defect or harness fix). **Run 6 is the evidence run**:
111 PASS, **1 error** (the recorded #345 product finding, remediated
in-run), 2 warnings (the remediation note + the inherited M2.5
delete-retention observation). All six legs executed to completion;
teardown verified the host clean (no cloud-hypervisor processes, no
new links, no new nft tables).

Leg-by-leg (single guest `qual-vm-1`, CH pids as observed):

- **Leg A — full lifecycle**: create-and-boot (fresh `vm create` sets
  desired `Running`), kernel banner + logind evidence; reboot is
  guest-level with the **same CH process** (713499); graceful stop
  (~32 s orderly shutdown, logind-gated); second start re-spawns a new
  CH (714495) with a third boot's banner + logind evidence.
- **Leg B — S1 agent SIGKILL while Running**: CH survived the crash
  (714495), the restarted agent re-adopted the same pid, exactly one
  CH process, identity constant, operation history unchanged
  (ops=5 events=15).
- **Leg C — control-plane restart while Running**: CH unaffected and
  same-pid across the restart, agent reconnect, identity constant,
  operation history unchanged.
- **Leg D — 60 s management-plane outage**: BFF/API refused
  connections for the full window, guest kept executing (cputime
  advanced), same CH process, and after restore the deferred-report
  queue drained **28 queued → 0 in 2 s** (one reconnect flush batch);
  operation history unchanged.
- **Leg E — four-daemon cold restart**: CH orphaned but alive after
  the full stack stop; the restarted stack's cold reconcile re-adopted
  the running CH (714495), node visible and Healthy, identity
  constant, operation history unchanged — *after a fully healed
  outage* (drain gate, §4 run 4).
- **Leg F — stop → delete**: logind-gated graceful stop accepted; the
  **#345 wedge fired exactly as characterized** (CH alive with a dead
  API after the stop reported success) and was cleared by the
  documented operator escape (SIGKILL), after which the post-stop
  assertions pass — no CH process remains, desired state Stopped;
  delete accepted, post-delete snapshot deterministic
  (ops=6 events=18, no CH process), with the M2.5 deferred-scope
  delete retention re-observed (`qual_warn`, not a gate).

Operation-history determinism held across every restart leg (the
ops/events counts and BFF task-list fingerprint never changed except
for the legs' own operations). The single error is the recorded
product finding #345 — not a harness or assertion defect — and the
run is reproducible via the committed scripts
(`deploy.sh --exec m4.3-lifecycle.sh` against the frozen candidate
`baa20c0e`).

## 4. Findings

### Run 1 (harness gap, fixed before run 2)

**deploy.sh's controlplane.toml never set `agent_socket_pattern`,
`agent_runtime_dir`, or `firmware_path` — VM dispatch was impossible in
the throwaway-dir layout.** The candidate's defaults for these keys match
the production layout (`/run/chv/agent/api.sock`, `/var/lib/chv/agent`,
`/var/lib/chv/hypervisor-fw` — install.sh verifiably places the firmware
there), so packaged installs are unaffected; but deploy.sh deliberately
deploys into a per-run `TEST_DIR`, and the CP then tried to reach the
agent at `/run/chv/agent/api.sock`: every `CreateVm`/`StartVm` dispatch
failed with `backend unavailable: agent — transport error`, retrying on
the orchestrator's loop. The M4.1 deployment smoke never dispatched a VM
operation (its scope was enrollment/readiness), so the gap was invisible
until this milestone. The M2.5 qualification that proved the lifecycle
ran on the host-local kvm-smoke.sh layout, which used the production
socket paths — the gap was introduced when that shape was committed as
deploy.sh with throwaway dirs.

Fixed in deploy.sh (harness-side; candidate unchanged): the generated
controlplane.toml now sets `agent_socket_pattern`,
`agent_runtime_dir`, and `firmware_path` to the deployment's actual
paths. Class: harness configuration, not a product defect.

Two smaller harness bugs found by the same run and fixed:
- `chvctl vm list --output json` prints the **bare items array** (not a
  `{"items": [...]}` wrapper) — the scenario's JSON parsing expected the
  wrapper and every VM assertion read empty;
- a fresh `vm create` sets `desired_power_state = 'Running'`
(create-and-boot semantics — the CP dispatches `CreateVm` then `StartVm`
as one flow), so the post-create identity assertion must expect
`Running`, not `Stopped`.

### Run 2 (product finding — issue #339; harness works around it)

**`chvctl image import --url …` → `chvctl vm create --image <name>` is
broken end-to-end in the candidate.** With the dispatch path fixed, the
`CreateVm` operation reached the node and failed with
`image file not found at resolved path: /var/lib/chv/images/ubuntu-noble.
Import the image first.` — although `image import ubuntu-noble` had
succeeded. Three independent defects in the chain (filed as
[kubedoio/chv#339](https://github.com/kubedoio/chv/issues/339) with the
full reproduction):

1. **Key mismatch**: chvctl `image import` sends `"url"`; the BFF import
   handler reads `"source_url"` and defaults to `""` — the URL is
   silently dropped and the images row is stored with an empty
   `source_url` (verified by reading the CP DB: `('3e6b3b58',
   'ubuntu-noble', 'disk', 'qcow2', …, '', …)`).
2. **Lookup by UUID, not name**: the BFF create-time resolution queries
   `WHERE image_id = ?` — the generated short UUID — while the operator
   references the image by the name chosen at import.
3. **`file://` rejected as remote**: even with the URL stored, the
   local-path test is `source_url.starts_with('/')`, so a `file://` URI
   falls into the "remote URL … download the image to the node first"
   rejection.

The failure is also **deferred and misattributed**: `vm create` returns
success (desired state accepted) and the error surfaces later in the
node-side operation, with a message telling the operator to do what they
just did.

Classification: product defect (MAJOR for the name-based workflow). The
frozen candidate is qualified via the documented operator escape hatch —
`vm create --image /absolute/path` passes through verbatim and stord's
path allowlist covers the qualification images dir — so M4.3 does not
depend on the broken chain. The fix (chvctl key, BFF alias + name
lookup + `file://` acceptance) lands post-rc1 on main, tracked in #339.

### Run 3 (product finding — issue #341; harness made zombie-aware)

**The graceful stop leaves an unreaped VMM zombie.** After the orderly
guest shutdown (~32 s, the snapd stop inside the agent's 60 s graceful
window), the CH process exits but nothing reaps it: `/proc/<pid>`
lingers in state `Z` with an empty cmdline until the *next*
`vm start` runs `prove_exited`. A VM that is stopped and never
restarted therefore leaks a zombie for the agent's lifetime. Filed as
[kubedoio/chv#341](https://github.com/kubedoio/chv/issues/341); fix on
main post-rc1 in [#342](https://github.com/kubedoio/chv/pull/342)
(take the child out of the surviving entry as `VmmChild::Dead` and reap
it in a detached task). Harness-side, `ch_alive` was made zombie-aware
(state `Z`/`X` = gone) — a zombie holds no fds and owns nothing, so
for lifecycle purposes it is gone; the product fix removes the leak
itself.

**Same run, harness bug (severity: every prior residue check was
vacuously green):** `count_cloud_hypervisor_processes` /
`assert_no_ch_residue` used `pgrep -x cloud-hypervisor` — but
`/proc/<pid>/comm` is truncated to 15 characters
("cloud-hypervis") against the 16-character name, so an exact-name
match **never fires** and the count was always 0. No earlier milestone
ever ran a CH on the qualification host (M4.1/M4.2 were
deployment-smoke scope), so the checks were unfalsified until this
run. Fixed in `lib.sh` (and later in `deploy.sh`'s teardown — see run
5): an anchored full-cmdline pattern,
`pgrep -f '(^|/)cloud-hypervisor( |$)'`, which cannot match the
harness's own `pgrep`/`zsh` invocations and treats zombies (empty
cmdline) as gone, consistently with `ch_alive`.

### Run 4 (product finding — issue #343; Leg E gated on report flush)

89 PASS, zero failures through Legs A–D (full lifecycle including
reboot-same-CH-pid, graceful stop + re-spawn, S1 agent-SIGKILL
adoption of the same CH pid, CP restart, and the 60 s outage with
deterministic operation history). **Leg E (four-daemon cold restart)
failed**: the restarted agent adopted the orphaned CH, then exited
with

```
Error: Migration(Unsupported("pending_control_plane"))
```

and never bound its API socket. Root cause (verified against the
preserved deployment's cache — 28 queued `NodeStateReport`/
`VmStateReport` messages): the runtime's deferred-report feature
(persisted on every defer during the Leg D outage) populates exactly
the field that the legacy-import invariant rejects, and the candidate
runs that import validation on **every boot** — `prepare_activation`'s
`(cache, core.db exists)` arm executes
`cache.map(plan).transpose()?` on the live NodeCache *before*
`activate_existing` can apply the M2.2b contract that defines the same
file as a compatibility projection whose content must not gate
activation. Any agent restart with an unflushed report queue — the
exact "outage → stack restart / node reboot / agent crash" recovery
path the deferral feature exists for — bricks the node until an
operator repairs `agent-cache.json`. Filed as
[kubedoio/chv#343](https://github.com/kubedoio/chv/issues/343); fix on
main post-rc1 in [#344](https://github.com/kubedoio/chv/pull/344)
(a host-bearing authority degrades an unplannable projection to a
warning; host-less and initial-import arms stay fail-closed; the
archive/checksum/identity proofs are unchanged).

Harness handling: the scenario now ends Leg D with an **outage-heal
gate** — the deferred-report queue must drain to zero (live
observable: the agent persists `agent-cache.json` on every defer and
on the reconnect flush, which is one batch) before Leg E stops the
stack. Run 5 measured 28 queued → 0 in 2 s. The claim is narrowed
accordingly: **cold reconcile is proven after a fully healed outage**;
cold restart with unflushed reports is recorded as residual risk (§5).

### Run 5 (product finding — issue #345; wedge detection + remediation)

108 PASS; Legs A–E fully green, including the four-daemon cold
reconcile that failed run 4 (drain gate: 28 → 0 in 2 s). **Leg F
failed**: the final graceful stop of the adopted VM completed (guest
powered down in ~31 s — the orderly signature; console truncation
logged) **but the CH process stayed alive** (state `S`) with a dead
API socket for 4+ minutes, until the teardown's link deletion killed
it indirectly. Follow-ups, all reproduced in isolation on a held
deployment (`m43-exp2`):

- the agent's stop loop ended on its **dead-socket premise** ("CH
  process disappeared — treat as stopped"): the request failing does
  not imply the process died;
- a subsequent `vm start` was **accepted but silently did nothing**
  (the re-spawn is refused because `prove_exited` sees the live pid and
  its cmdline still proves identity — the same deferred-silent-failure
  class as #339);
- **SIGTERM is ineffective** on the wedged VMM (its handler routes
  through the stuck control loop); only SIGKILL clears it;
- control: the same stop on a freshly **spawned** VM works — CH exits
  with the guest ~2 s after `Shutdown` (the RC2 premise); the failure
  appears specifically after **adoption**.

Filed as [kubedoio/chv#345](https://github.com/kubedoio/chv/issues/345);
fix on main post-rc1 in
[#346](https://github.com/kubedoio/chv/pull/346) (the stop verifies
liveness after the loop via `prove_exited` and SIGKILLs + waits out a
survivor under the lifecycle op lock; the re-spawn refusal on `Alive`
is unchanged — never double-spawn against a live VMM).

Harness handling: `wait_guest_down` detects the wedge signature
(process alive **and** `vm.info` unreachable on 3 consecutive polls —
3 strikes avoid racing the normal ~2 s exit) and remediates with
SIGKILL, the documented operator escape, so the leg's remaining
delete/determinism assertions still execute; the finding itself is
recorded as a run error, not papered over.

Same run, three latent teardown bugs in `deploy.sh` (all harness-side,
fixed): the cleanup's `pkill -x cloud-hypervisor` never matched (the
same 15-char comm truncation as the lib.sh counter — nothing was ever
killed by that line), the link-deletion fallback only matched
`br-*`/`tap-*` and missed `chvbr0` (the default network's bridge name
per `chv-hypervisor-api` `resources.rs`), and no nft-table fallback
existed at all. All three were masked in clean runs because nwd
removes its own links/tables on SIGTERM; they only matter when
something else (a wedged CH) holds the bridge. The cleanup now kills
test-dir-scoped CH processes with `pkill -f` plus a SIGKILL fallback,
deletes `chvbr*` links, and removes baseline-diff'd nft tables.

## 5. Residual risk / not claimed

- **Cold restart with unflushed deferred reports bricks the agent
  (#343).** Leg E is proven only after a *fully healed* outage — the
  drain gate requires the deferred-report queue to reach zero before
  the stack stops. Not claimed: a crash, node reboot, or operator
  restart racing an unhealed outage (an unflushed queue). The frozen
  candidate fails closed there until an operator repairs
  `agent-cache.json`; fix on main in
  [#344](https://github.com/kubedoio/chv/pull/344).
- **Graceful stop of an adopted VM wedges the VMM (#345).** The final
  run records this as its single error and remediates it in-run with
  SIGKILL (the verified operator escape). Not claimed on the frozen
  candidate: a clean post-adoption stop, and a post-adoption start
  after a wedged stop. Fix on main in
  [#346](https://github.com/kubedoio/chv/pull/346); the CH-side wedge
  (v43 control loop hanging after guest poweroff) is contained, not
  cured, by that fix.
- **Host reboot itself is not provable on this topology** (the
  qualification host is itself a disposable guest; rebooting it ends
  the run). Leg E — all four daemons stopped and restarted, cold
  reconcile re-adopting the orphaned CH — is the labeled subset, per
  plan §6.
- **Nested virtualization only.** All guest virtualization ran through
  `/dev/kvm` inside a KVM guest (explicitly enabled for this
  campaign). Bare-metal KVM behavior is not separately evidenced by
  this milestone.
- **Single VM, single node, serial lifecycle.** One guest, one agent,
  one operation at a time; concurrent multi-VM churn, scheduling
  pressure, and multi-node behavior are out of scope (M4.6+/later).
- **Delete retention (inherited M2.5 deferred scope, re-observed).**
  `vm delete` removes the authority-side state but the BFF list row,
  CP row, vm dir, and volume remain — recorded as `qual_warn`, not a
  gate, per the M2.5 scope decision.
- **Timing margins.** Boot and shutdown budgets carry nested-KVM
  margin (420 s kernel banner vs the M2.5 300 s budget); within those
  bounds a slow-but-healthy guest and a pathological one are
  indistinguishable to the harness until the timeout fires.

## 6. Post-milestone review follow-ups

A comprehensive review of the merged milestone range
(`e9872227..a354d1e6` — the four product fixes plus this milestone's
harness and docs) ran after the milestone closed. Every finding was
fixed on main (post-rc1, like the fixes it hardens), tracked, or
explicitly accepted as designed:

- **[#348](https://github.com/kubedoio/chv/pull/348)** — the #346
  wedge SIGKILL now carries the exe cross-check (it was the only
  production kill site without it), and a refused or ineffective kill
  fails the stop loudly instead of reporting success over a live VMM
  (the #345 bug class, reachable through the remediation's own
  refusal path — e.g. a VMM binary replaced on disk while the process
  ran). The live handle is restored into the entry on failure, so
  re-spawn protection holds. Regression test:
  `stop_vm_graceful_fails_loudly_when_kill_is_refused`.
- **[#349](https://github.com/kubedoio/chv/pull/349)** — image-chain
  hardening: an `image_id` hit terminates the create-time lookup (no
  silent resolution to a name-colliding image when the id row has no
  usable source), import canonicalizes and dedups `file://` forms, and
  an empty/NULL source errors truthfully.
- **[#350](https://github.com/kubedoio/chv/pull/350)** — harness
  robustness: the drain gate's cache path is env-passed (a parse break
  previously weakened Leg E's #343 gate into a silent 240 s timeout),
  and the teardown residue kill carries the argv[0] anchor.
- **[#352](https://github.com/kubedoio/chv/pull/352)** — CI job
  timeouts (rust 45 m, ui 15 m): during this review a transient apt
  mirror hang burned a CI runner for six hours on an otherwise healthy
  PR; hangs now fail fast.
- **[#351](https://github.com/kubedoio/chv/issues/351)** — tracked,
  not fixed: `delete_vm`'s force path still silently tolerates a
  refused kill (same class as #348's finding, lower likelihood,
  pre-existing).
- Accepted as designed (no change): the intentional unquoted
  `nft delete table` word-splitting in `deploy.sh` teardown, and the
  `ch_alive` pid-recycle TOCTOU (its failure direction is a visible
  timeout, never a silent pass).

The PR-branch tree (all of #348's changes) was re-validated locally
after the review: `cargo test --workspace` — 1445 passed, 0 failed;
`cargo clippy --workspace --all-targets -- -D warnings` clean. The
merged main combination is validated by the post-merge CI runs on
`9ecb3f07`/`81c68feb`.

No evidence claim in this document changes: the run-6 results (§3)
were produced by the frozen rc1 candidate (`baa20c0e`) and stand as
