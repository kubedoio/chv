| File | Role |
|---|---|
| `scripts/integration/qual/lib.sh` | shared logging/assertions, wait loops, hermetic chvctl wrapper (isolated `XDG_CONFIG_HOME`), sqlite helpers (python3 stdlib — no sqlite3 CLI dependency; **read-only URI for live reads**, see §5), bcrypt helper, forbidden-outcome residue checks |

| `scripts/integration/qual/deploy.sh` | candidate-path deployment (M2.5 shape as code): certs, stop→seed→restart DB seeding, core-managed authority, verification, teardown with residue assertions, `--exec`/`--hold` scenario hand-off |

Unlike the M2.5 harness (host-local, quoted in evidence), the prompt-04
harness is committed and reviewable; every later milestone's evidence cites
these scripts at the exact SHA. shellcheck-clean (0 errors/warnings).

Key invariants encoded in the harness:

- **No `CHV_ALLOW_INSECURE`** — deploy.sh asserts it is absent from the
  environment; production binaries refuse it (prompt 03).
- **Real mTLS**: a pre-placed client cert is used only for the EnrollNode
  handshake; the deployment asserts the *control-plane-issued* node
  certificate (`CN = <node id>`) appears in the agent runtime dir and that
  the one-time bootstrap token is consumed exactly once (DB check).
- **Core-authority contract**: `authority_mode = "core-managed"`, agent
  runtime dir `0700` (`cellhv-core-startup::validate_paths`), explicit
  `core_store_path`/`core_archive_path`/`core_api_socket_path` (defaults
  point at `/var/lib/chv/agent`, which does not exist in a throwaway
  deployment).
- **Forbidden-outcome teardown**: no cloud-hypervisor processes, no new host
  links, no new nft tables (baseline-diff before/after the deployment);
  nwd-owned `br-*`/`tap-*` links created by the run are deleted before the
  assertion.

## 5. Findings during harness bring-up (all resolved or filed)

1. **X.509 v1 client certs break rustls mTLS** — `openssl x509 -req` without
   `-extfile` emits v1 certificates; rustls/webpki rejects them
   (`UnsupportedCertVersion`) during the EnrollNode handshake. Harness fix:
   every cert is minted v3 with explicit basicConstraints/keyUsage/EKU.
   (This host has OpenSSL 3.0.13; the older kvm-smoke.sh shape relied on the
   previous box's toolchain behavior.)
2. **Core path config keys** — `core_store_path`/`core_archive_path` default
   to `/var/lib/chv/agent/…`; a throwaway deployment must set them
   explicitly or the agent dies at startup with an Io error. Harness sets
   all three core paths inside the test dir.
3. **SQLite WAL unlink hazard (filed as #321)** — an external read-write
   connection to the live control-plane DB unlinks `-wal`/`-shm` on close
   (verified with strace); the CP's pool connections then commit into the
   unlinked inode and the data is lost at exit. The original smoke failed
   exactly this way: enrollment succeeded but neither the node row nor the
   token consumption were visible. Harness workaround: seeding happens in a
   stop→seed→restart window, and all live reads use `mode=ro` URIs (which do
   not unlink). Read-only opens are safe; the operational hazard for
   operators is documented in #321.
   **Re-verified post-rc1 (2026-10-01, fix round for #321)**: the recorded
   mechanism does not reproduce on the current build. Controlled
   experiments (python sqlite3, a bare sqlx pool, and a live
   `deploy.sh --exec` scenario against the real control plane holding 9
   open DB fds) all show SQLite removing `-wal`/`-shm` only when the
   *last* connection closes — an external read-write open+write+close
   while the CP's pool holds connections leaves the sidecars linked, and
   both the external write and subsequent CP commits are visible to fresh
   readers. The genuinely losing state was verified separately: if the
   sidecar files are removed by *direct file operations* while CP
   connections are open (a script `rm`-ing `-wal`, a `cp` over the DB),
   the pooled connections keep committing into the deleted inode with no
   error and the data is lost. The smoke failure itself was real, but its
   attribution to the external-close unlink is no longer supported; the
   harness's stop→seed→restart discipline and `mode=ro` reads remain
   correct practice either way. Disposition: documentation fixed
   (OPERATIONS.md "Live Database Access": read-only URIs for live reads,
   stop-window for manual writes, never touch sidecar files directly);
   issue #321 closed with the verification record.
4. **`chvctl health` surface gap (filed as #320)** — all three
   `chvctl health` subcommands target BFF routes that are not implemented
   (501/404 NOT_IMPLEMENTED). Not a deployment failure; the harness gates on
   node `state: TenantReady` + `health: Healthy` from the node list instead.
   **Fixed post-rc1 (2026-10-01)**: the three viewer-tier GET routes are
   implemented (`/v1/health`, `/v1/cluster/health`,
   `/v1/nodes/{id}/health`, read-only aggregates over the store) and
   verified live — a `deploy.sh --exec` scenario against a fresh
   deployment ran `chvctl --output json health check|cluster|report`
   successfully (status ok, database reachable, total_nodes 1, node
   TenantReady) with zero-residue teardown; integration tests boot the
   real router (auth, aggregation, dominance, 404).
5. **Harness robustness** — `set -e`/`pipefail` landmines fixed during
   bring-up: bare `assert_*` calls aborting cleanup, `pgrep` exit 1 in
   pipelines on the *desired* no-match outcome, command substitution inside
   `wait_for` arguments expanding once. All guarded; shellcheck clean.
