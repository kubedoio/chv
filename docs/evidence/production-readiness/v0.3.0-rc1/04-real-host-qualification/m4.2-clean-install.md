## 1. Scope and method

| Leg | What | Where |
|---|---|---|
| A — static contract | install the candidate `.deb`s into a **clean** Ubuntu noble system and assert the packaging contract: service users, groups/memberships, directories with exact modes/ownership, systemd units (+ hardening keys), binaries, conffiles, migrations, tmpfiles, versions | clean container (debootstrap noble + systemd-nspawn) on the qualification host |
| B — boot | boot the container with systemd, enable + start the four packaged units with the **packaged** configs, record honest outcomes | same container |
| C — host smoke | `kvm-smoke.sh --packages`: install the `.deb`s on the qualification host itself, bring up the stack with dev configs against real `/dev/kvm`, health-check, remove packages | qualification host |

Honesty labels:

- The "clean system" is a fresh debootstrap of Ubuntu noble booted under
  `systemd-nspawn` **on the same physical host** as all other prompt-04
  evidence (4 vCPU / 7.8 GiB / kernel 6.8.0-139). It is a clean *guest*
  environment, not a separate machine.
- The container has no `/dev/kvm`; Legs A/B prove the packaging + systemd
  contract only. No KVM, VM-lifecycle, or performance claims derive from
  them. Leg C uses the real host KVM but the legacy dev-config shape
  (throwaway dirs), not the qualified security path — no enrollment or
  authority claims derive from it (those come from M4.1 / M4.3).
- Packages alone are **not** claimed to yield a working deployment: §3
  documents the packages↔`install.sh` boundary (fail-closed control plane
  without CA/certs).

### Harness (committed code)

- `scripts/integration/qual/clean-install.sh` — Legs A+B. Caches a
  debootstrap base tarball (`nspawn-base-noble.tar.gz`, 188M) for fast
  re-runs; unpacks a fresh root per run; stages `.deb`s under `/root`
  (systemd-nspawn mounts a fresh tmpfs over `/tmp`); resolves uid/gid
  numerically against the **container's** passwd/group (host and container
  allocate system users independently); boots with a one-shot verify unit
  that captures `systemctl show` (label-form), per-unit journal tails, a
  process snapshot, `/run` contract stats, sockets, versions, and redacted
  configs, then powers off. shellcheck-clean (warnings level, matching the
  other qual scripts).
- `scripts/integration/kvm-smoke.sh` — Leg C (`--packages` mode, pre-existing
  harness; two bugs fixed in-repo this milestone, §4).

Full transcripts preserved on the qualification host:
`/var/lib/chv/qual/nspawn-{install,boot,results}.log|txt`,
`/var/lib/chv/qual/debootstrap.log`.

**Leg B (boot with systemd, packaged configs, no install.sh):
errors=0, warnings=3.**

- **Control plane fails CLOSED** (expected boundary): with no
  `install.sh`-generated CA/certs and a placeholder `jwt_secret`, every
  start exits with the typed error
  `Error: Internal("failed to read CA certificate: No such file or directory")`
  and `Restart=on-failure` cycles — no panic, no insecure fallback. The
  packages↔`install.sh` boundary is thus: packages provide layout; a
  working control plane requires `install.sh` (or documented operator
  steps: CA + server/client certs, real `jwt_secret`, admin seeding).
  Also logged (recorded, prompt-03 known behavior):
  `WARN credential_crypto: Neither CHV_ENCRYPTION_KEY nor CHV_JWT_SECRET is set; S3 credentials will be stored in plaintext`.
- **chv-agent runs** (`ActiveState=active`): defers control-plane reports
  without enrollment material (`io error on /run/chv/agent/agent.crt`),
  holds the durable `/run` contract — `/run/chv/agent` 0775 `chv:chv`,
  `/run/chv/core` 0700 `chv:chv` (tmpfiles.d + unit) — and listens on
  `/run/chv/agent/api.sock` + `127.0.0.1:9901` (metrics) per the packaged
  config. Reconcile logs show `stord_ok=false nwd_ok=false` churn (see
  next bullet) — recorded, not asserted.
- **chv-stord / chv-nwd systemd units do NOT come up on a clean install**
  (known findings, WARN in harness):
  - `chv-stord.service` (`User=chv`) cannot open
    `/var/lib/chv/storage/localdisk/stord.db` — postinst owns the storage
    dirs `chv-stord:chv-stord` 0750 (**#323**). Directly confirmed:
    `runuser -u chv -- touch …/localdisk/probe` → `Permission denied`,
    while `runuser -u chv-stord` succeeds.
  - `chv-nwd.service` fails `226/NAMESPACE`:
    `Failed to set up mount namespacing: /run/netns: No such file or
    directory` — `ReadWritePaths` references `/run/netns`, which nothing
    in the packages (or `install.sh`) creates (**#324**). Reproduced on
    three independent clean boots.
  - Because the units never bind their sockets, the agent **spawns and
    supervises its own stord/nwd children** (process snapshot: ppid =
    chv-agent, configs under `/var/lib/chv/agent/chv-{stord,nwd}.toml`)
    and those children hold `/run/chv/{stord,nwd}/api.sock`. A working
    fallback, but the enabled units keep crash-looping and the two
    supervision models are in unresolved conflict.
- Full per-unit journal tails, `systemctl show` properties, socket list,
  versions, and redacted packaged configs (jwt/encryption keys redacted)
  are in `nspawn-results.txt`.

Two committed-harness bugs found by this leg and **fixed in-repo**
(scripts-only, no product change):

1. kvm-smoke minted X.509 **v1** leaf certs (`openssl x509 -req` without
   `-extfile`); the candidate's fail-closed rustls rejects them, so the
   control plane refused to start (`TLS configuration failed: transport
   error`). Same root cause as the M4.1 deploy.sh bring-up note; fixed the
   same way (extfile with basicConstraints/keyUsage/EKU/SAN → v3).
2. kvm-smoke's EXIT-trap cleanup aborted at the bridge-removal pipeline
   when no test bridges exist (`grep` no-match under `set -e -o pipefail`),
   leaving packages installed and the test dir behind — observed on the
   first (failed) run; fixed with a pipeline-level `|| true`.

### Decisions

- **#323 (user vs. ownership model)**: stord keeps `User=chv`. Rationale:
  the stord API socket is mode `0600` with chv-agent as its only client
  (`chv-stord-core/src/server.rs`), and cloud-hypervisor (spawned by the
  agent as `chv`) must read/write volume files — a dedicated `chv-stord`
  runtime user would require a group-accessible socket plus
  group-writable volumes, i.e. a redesign with real-KVM validation (M4.4+
  territory). Storage dirs are now `chv:chv-stord 0770` (group kept as
  the seam for that future model) in both postinst and `install.sh`;
  `/run/chv/stord` is `chv:chv 0755`. The `User=chv` rationale is
  documented on the unit. `docs/examples/systemd/` (shipped in the
  release tarball via `build-release.sh` and referenced by
  `DEPLOYMENT.md`) is synced with `packaging/systemd/` — the tarball
  previously carried a stale `User=chv-stord` stord unit and a pre-Core
  agent unit. `chv-agent` now orders `After=/Wants=` stord+nwd so the
  agent's fallback supervisor finds listening sockets and skips spawning
  (verified in the Leg B journal below).
- **#324 (unit start failure)**: `/run/netns` is created `root:chv 0770`
  by the packaged tmpfiles.d entry. During the fix review a *runtime*
  gap was found and filed as **#328**: `ip netns add` additionally needs
  `CAP_SYS_ADMIN` for `mount --make-shared` (proven directly on the
  qualification host: as `chv` with exactly the unit's cap set the call
  fails `EPERM`; with `CAP_SYS_ADMIN` added it succeeds). Capability
  grants are security-relevant — left to maintainer decision, expected
  to be driven by M4.4 real-KVM evidence.
- **#325 (postinst grep)**: membership guards match the group list
  per-entry (`id -nG | tr ' ' '\n' | grep -qx`). The same typo-prone
  pattern was hardened in the kvm/disk guards (the fix itself initially
  mis-targeted the kvm needle and was caught by this harness — the
  validation loop works).
- **#326 (authority default)**: `docs/examples/agent.toml` (packaged
  config source) and the `install.sh`-generated config now default
  `authority_mode = "core-managed"`, matching the prompt-02
  single-authority release claim. Core-managed starts on a bare install
  (Core store paths are postinst-provisioned) and defers enrollment —
  mirroring the control plane's fail-closed boundary. The agent logs a
  warning when legacy is selected explicitly. The `chv-config`
  omitted-key default stays legacy (dev/compat default, own strictness
  test); every shipped configuration surface selects core-managed.
