## 1. Scope

The prompt-04 reusable storage contract —
`validate → provision/consume → attach → guest write/read → restart/interruption → recover → detach → cleanup → repeat`
— for the two declared profiles:

- **Local file, VM-integrated** (the only VM-reachable storage class today): a VM's
  boot volume provisioned from a seed image through the full BFF → CP journal →
  agent → stord → cloud-hypervisor chain, with guest-visible write/read proof.
- **LVM, stord layer only** (loopback PV → VG → LV): the `LVMBackend`'s real contract
  exercised directly against stord (open/export, block write/read, COW snapshot,
  clone, resize, read-only policy, cleanup, repeat).

**Not claimed:** Ceph RBD, iSCSI (declaration §3 non-scope); snapshot/clone
*execution* on core-managed nodes (fail-closed by design — §4/#378); LVM as a
VM-attached storage class (#379).

## 4. Findings

Five product findings (three fixed and merged during the milestone, two recorded with
design direction), plus the harness traps that produced false failures along the way.

### 4.1 #374/#375 (merged) — all-digit VM ids crash cloud-init's NoCloud datasource

The agent wrote the `vm_id` UNQUOTED into the seed's meta-data; an all-digit id
(probability ≈ 2.3% per VM for the 8-hex-digit ids) YAML-parses as an integer and
crashes cloud-init 26.1 (`AttributeError: 'int' object has no attribute 'replace'`),
discarding the entire DataSourceNoCloud — userdata and network-config silently never
applied. M4.4 missed it because those VM ids contained letters. Proven by a standalone
repro (qemu-nbd mount of the guest root + `/var/log/cloud-init.log` traceback) and an
A/B control (default userdata also failed → meta-data typing was the trigger). Fix:
`cloud_init_meta_data(vm_id)` quotes both values; unit tests pin string-typed YAML.

### 4.2 #376/#377 (merged) — supervisor-respawned stord loses path confinement and relocates runtime_dir

When the agent's supervisor respawns a dead stord it generates a minimal
`chv-stord.toml`. `path_allowlist` is `#[serde(default)]` and an absent key means
**allow-all** — so a freshly deployed stord was path-confined (per the operator's
stord.toml) while a respawned one silently was not. The generated config also sets
`runtime_dir` to the *agent* dir, so the sessions DB (and the local backend's
snapshot/clone destination files) relocate on restart; the agent compensates by
re-driving volume opens (observed), but two `stord.db` files with disjoint session
rows remain an operational trap. Fix (#377): `AgentConfig.stord_path_allowlist`
(operator-configurable — there is no static safe default because seed paths are
per-spec) written into the generated config when non-empty; the qual deploy and
`install.sh` both set it to mirror their stord config; the scenario now asserts
parity across the restart. The runtime_dir relocation is recorded as current truth.

### 4.3 #380/#381 (merged) — volume clone could never succeed

`lifecycle.clone_volume` journaled a `CloneVolume` op and then INSERTed a
`volume_desired_state` row for the **target** volume id — but nothing ever created
the target's `volumes` row, so the FK always violated, surfacing as a confusing
404 `volume with id {target} not found`. Reproduced on a held deploy; fix (#381)
validates up front (source exists, target must not — no op journaled on rejection)
and materializes the target via the same `upsert_volume` the volume-fragment
reconcile uses (one tx: `volumes` row with the source's shape + VDS intent row).
Live-validated: `chvctl volume clone` → accepted, rows present.

### 4.4 #378 (recorded, not fixed) — snapshot/clone accepted-then-fails-closed on core-managed nodes

Single-writer enforcement is correct: the agent's legacy volume-op RPCs fail closed
in core-managed mode ("Core M1 does not model it"), and the reconcile path that
would execute them is also legacy-only. The gap is the acceptance UX: the BFF
accepts, the CP journals the intent, the orchestrator retries the refused dispatch
(3 retries, 10/20/40 s backoff; the 600-second stuck-operation reaper then resets
the op Running → Accepted, where it re-claims), and the operator sees success then
silence. Leg D now
*asserts* the boundary (accepted + journaled + `unsupported in core-managed mode`
in the CP log + no file materialized — an architecture violation if that ever
flips). Fix direction on the issue: reject at accept-time (requires the CP to know
node authority mode, e.g. via node inventory).

### 4.5 #379 (recorded, design decision) — LVM is unreachable from the VM lifecycle

The agent opens every VM volume with the hardcoded backend class `"local"`
(`reconcile.rs:934`, `:1134`); there is no volume-create API (volumes only exist as
implicit VM boot disks); the LVM VG must be pre-provisioned out-of-band. The LVM
backend is qualified dead code from a user's perspective — correct, tested,
unreachable. Making it reachable is a volume-model design decision (storage-class
selection + Core modeling volume ops, which would also unlock #378).

### 4.6 Harness traps (fixed in the scenario; recorded for future legs)

- `chvctl --memory 1024` is **1024 bytes** (`parse_size_bytes`: bare numbers are
  bytes) — created a VM with 1 KiB of RAM that CH accepts but can never boot (empty
  console, `vm.boot` 500). Always suffix (`1024M`).
- Clone target ids must fit `ResourceId`'s 16-byte cap — a 19-char id is rejected
  before journaling with a bare 500.
- An unguarded `/proc/$pid/cmdline` read with an empty pid resolves to
  `/proc/cmdline` — the **host** kernel's cmdline (this host is itself a nested
  guest, hence `BOOT_IMAGE=...`).
- The stord-restart wait must require a non-empty new pid — `!= old-pid` passes on
  empty output during the dead-old/not-yet-spawned-new window.
- Graceful stop truncates console.log — boot counting across stop/start is
  unreliable; wait for contract lines (READBACK, logind) instead.
- `wait_for` evaluates args once (per-poll functions); `pgrep -x` never matches
  "cloud-hypervisor" (comm truncation); console.log is binary (`grep -a`); `mktemp`
  templates need the `XXXXXX` suffix; sqlite reads on live DBs need the read-only
  URI.
- Residue counts must not default failures to zero (`${var:-0}` turned an
  unreadable sessions DB into a "no sessions remain" pass — caught by review of
  #382); absence checks need a live source, not a swallowed error.
- `cargo test --no-run | tail` only propagates failure under `set -o pipefail` —
  without it a stale test binary from a previous build can be picked up.
- Known cosmetic, shared with the m4.4 idiom: `wait_for … && qual_pass … ||
  qual_error` double-reports a timed-out poll (two FAIL lines) — accounting noise
  only, recorded not fixed.

## 5. Layer truths (as-operated, for the record)

- **Local backend provisioning:** seed conversion materializes as an intermediate
  qcow2, then converts to raw and `set_len`s to capacity — wait for
  `stat size ≥ capacity`, not file existence.
- **Snapshot/clone destination:** `{stord runtime_dir}/{volume_id}-{name}.img` —
  relocates with the daemon's runtime_dir (#376).
- **stord session lifecycle:** open_volume inserts a `sessions` row;
  close_volume (on VM delete) deletes it. Across a supervisor restart the DB
  relocates and the new daemon hydrates 0 sessions — the agent re-drives opens.
- **Read-only policy is one-way:** `blockdev --setro`, no `--setrw` path.
- **LVMBackend:** handle `lvm-{vg}-{vid}`, export `/dev/{vg}/{vid}`; snapshot
  `{vid}-snap-{name}` and clone `{vid}-clone-{name}` are both `lvcreate -s`
  COW snapshots (`-l 100%FREE` — needs free-extent headroom; the real-LVM tests
  run serially for this reason). The lvm_real tests pin **point-in-time
  independence** (origin writes never show through), not a copy mechanism.
- **VM-integrated volumes are local-file only** (#379).
- **M2.5 residual re-verified (Leg E):** VM delete retains the volume row (cascade
  absent) and the volume backing file — recorded as current truth, unchanged class.

## 6. Residual risk / not claimed

- Ceph RBD, iSCSI — not exercised, not claimed.
- Snapshot/clone/restore *execution* on core-managed nodes — fail-closed by design
  (#378); the accepted-then-silent-failure window (dispatch retried 3× with
  backoff, then the 600 s stuck-op reaper loop) is the recorded UX gap.
- LVM as a VM-attached storage class (#379); LVM qualified at the stord layer only.
- Cross-restart snapshot lifecycle edge: a snapshot created before a stord restart
  lives in the old runtime_dir while post-restart deletes compute the path in the
  new one (not exercised by the scenario; noted on #376).
- #368 (journaled-create wedge) — carried from M4.4, unchanged.
- Supervisor-stord / nwd fabric identity: the restarted agent logged "failed to
  fetch fabric identity from nwd" every 30 s for ~4 min in the run-6 preserved
  failure dir. nwd was alive and serving — the refusal is by **configuration**
  (`fabric overlay requested but the fabric provider is disabled in nwd
  configuration`, INVALID_ARGUMENT), i.e. a persistent feature/config mismatch,
  not a startup race; the ~4-minute window is just how long that failed run lived
  before teardown. Benign to the storage scenario (no storage path depends on the
  fabric identity), recorded here for completeness.
