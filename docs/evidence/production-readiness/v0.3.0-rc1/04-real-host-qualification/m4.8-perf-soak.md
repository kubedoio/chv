## 1. Scope

The prompt-04 milestone §M4.8: idle CPU/RSS per daemon; lifecycle operation
latency (distributions, not means); bounded concurrent API workload;
migration throughput on the qualified path; control-plane DB growth; open
fd/socket growth; log/metric cardinality; a bounded steady-state soak with
repeated operations — all sequential and resource-bounded on this host.

**The assertion vs record distinction (the milestone's core rule):**

- **ASSERTIONS (a failure fails the milestone)** — the soak/forbidden-outcome
  checks: zero residue after every soak cycle (zero cloud-hypervisor
  processes, tap count back to baseline, the cycle's stord session closed,
  both op journals terminal, exactly one CreateVm row); no fd/socket growth
  AT REST across the soak; no control-plane DB growth with zero ops; no
  unbounded log cardinality; every concurrent-workload request HTTP 200
  (a 5xx under bounded load is crash-class); the migration leg completes
  with digest + byte equality (its *speed* is a record, its *correctness*
  is an assertion).
- **RECORDS (labeled numbers, never pass/fail on magnitude)** — idle
  CPU/RSS, per-op lifecycle latency distributions, read/write latency under
  the bounded concurrency, migration MiB/s, DB sizes and per-op bytes,
  mid-soak fd/socket counts, VMM RSS, log bytes/min. A measurement being
  slow or large is NOT a failure unless it indicates unbounded
  growth/leak — those are errors per the pre-registered thresholds in §2.4.

**Not claimed (§6):** anything scale-shaped — concurrency, density or
throughput beyond the bounded N of §2.3; multi-node; the CP-orchestrated
migration path (out of scope per M4.6); M2.5 delete retention (BFF
rows/backings of deleted VMs persist by design — disclosed once in the
scenario, physical-side cleanup is what is asserted); host reboot (M4.3's
recorded not-provable subset); #394 concurrent-write migration (quiescent
seeded volumes only).

## 2. Harness (methodology pre-registered BEFORE the live run)

Same deploy shape as M4.3–M4.7 (`deploy.sh --exec`). The scenario adds
the M4.6 two-standalone-stord mTLS topology for the migration-throughput
leg (deliberately **not** agent-supervised, #385), with the same
pinned-and-verified grpcurl v1.9.3 provisioning (checked-in checksums
asset) and a 4 GiB patterned seed (1024 × 4 MiB chunks — the M4.6/M4.7
size, so the throughput record is comparable across milestones).

### 2.1 Legs

| Leg | Measures / asserts | Method |
|-----|--------------------|--------|
| P1 | Idle CPU% + RSS per daemon (control-plane, agent, stord, nwd) at rest, zero VMs | `/proc/<pid>/stat` utime+stime ticks (CLK_TCK-normalized) + `/proc/<pid>/status` VmRSS, 30 samples × 2 s = 60 s window; one python spawn samples all four daemons per tick so the sampler does not perturb the window. Plus: DB snapshot, idle log rate, fd/socket counts, `/metrics` series count, and the at-rest DB-growth assertion |
| P2 | Lifecycle latency distributions + the soak | N_SOAK=6 sequential create→start→boot-to-logind→stop→delete cycles (1 vCPU / 512 MiB guest, the m4.7 leg shape), 10 list+get read pairs per cycle while Running, zero-residue assertions after every cycle; per-op timings land in `lifecycle-latency.csv`; mid/end fd/socket + metrics samples; per-cycle DB sizes |
| P3 | Leak verdicts + post-soak idle | Repeat of P1; fd/socket growth vs P1 is the leak assertion (same net-zero-VM at-rest state); RSS growth record-only |
| P4 | Bounded concurrent API workload | 4 parallel reader loops (curl → BFF `POST /v1/vms` list + `POST /v1/vms/get`, per-request `http_code` + `time_total`) + 2 sequential writer loops (chvctl create→converge→delete) for 90 s against one anchored created-not-started VM; all-200 assertion; latency distributions + writer cycle counts records |

| P6 | Final sweep + summaries | zero CH processes, zero scenario taps, physical backings ↔ CP rows, live stord sessions closed, every journaled op terminal, one CreateVm row per created VM, log-cardinality verdict, DB growth summary, artifacts manifest |

### 2.2 Convergence signals (host truths, never submit-level answers)

Per-op latency is wall-clock **from API acceptance to convergence**, where
convergence is the M4.3–M4.7-proven host truth: create = boot-volume
backing at full capacity (`vm_volume_ready`); start = desired Running AND
`console.log` receiving bytes (payload pushed, firmware executing — not
the BFF's submit-level answer, the #368 lesson); stop = CH process gone
(the #345 wedge path degrades to SIGKILL remediation and the record
carries the flag); delete = CH gone + tap removed + stord session closed
(physical-side convergence — M2.5 retention means the BFF row legitimately
persists). Boot-to-banner and banner-to-logind are recorded as separate
ops. Client-observed accept RTT is recorded alongside (it includes the
chvctl process spawn; read latency is measured via curl + the
chvctl-stored JWT — the m4.4 precedent — so it measures the API, not CLI
startup).

### 2.3 N choices (sequential, resource-bounded on a 16 vCPU / 31 GiB host shared by all daemons + one guest at a time)

| Knob | Value | Rationale |
|------|-------|-----------|
| N_SOAK | 6 cycles | typical ~2.5–4 min/cycle (create seed-conversion ~10–25 s, boot to logind ~60–150 s nested, graceful stop ~35 s, delete+settle ~20 s) ⇒ 15–24 min |
| Idle windows | 2 × (30 samples × 2 s) = 2 × 60 s | brackets the soak at the same net-zero-VM at-rest state |
| READERS / WRITERS / window | 4 / 2 / 90 s | explicitly bounded-by-this-host, NOT a scale claim |
| SOAK_READS | 10 list+get pairs per cycle | steady-state read traffic while the VM runs |
| Migration volume | 4 GiB patterned | the M4.6/M4.7 size — comparable evidence |
| BULK_COPY sampling | 0.5 s | grpcurl spawn + sleep is the resolution limit |

**Projected runtime:** scenario ~30–40 min (P1 1.5 + soak 15–24 + P3 1.5 +
P4 ~4 + P5 5–7 + P6 ~1) + deploy ~3–5 min ⇒ **~35–45 min typical**, inside
the 45–60 min mandate with margin for slow boots (worst case ~55 min).

### 2.4 Pre-registered leak thresholds (interpretable verdicts, chosen before the run)

| Threshold | Value | Rationale |
|-----------|-------|-----------|
| FD_GROWTH_MAX | 24 fds | per daemon, P3-at-rest minus P1-at-rest (same net-zero-VM state). >24 across ~30+ ops ⇒ ≥0.8 fd/op leak; ≤24 covers pool warm-up and transient accept sockets |
| SOCK_GROWTH_MAX | 12 socket fds | same comparison, socket-scoped |
| IDLE_DB_GROWTH_MAX | 512 KiB | controlplane.db + -wal net growth across a 60 s at-rest window with zero API calls. SQLite WAL is reused after checkpoint (steady-state net growth = db page growth), so page-bounded noise stays far below this; row accumulation does not |
| NEW_LOG_SHAPES_MAX | 8 | NEW normalized message shapes in soak half 2 vs half 1, per daemon. Steady-state repetition adds zero shapes; per-op unique strings add ~1/op |
| LOG_SHAPES_TOTAL_MAX | 2000 | distinct normalized shapes per daemon across the run |
| METRIC_SERIES_MAX | 200 | Prometheus series at the agent's `/metrics` (the exporter is a fixed node-scoped gauge set; at-rest counts must also not grow across the soak, tolerance 10) |
| RSS growth at rest | record-only | allocator retention makes gating unsound; warn > 100 MiB |
| Idle log rate | record-only | warn > 256 KiB/min per daemon at rest |

Log-shape normalization: strip the leading timestamp, mask UUIDs / `0x…`
hex / all integers (ids, ports, durations, counters) — a repeated message
with varying values collapses to ONE shape. Known artifact: the byte-window
boundary can contribute ≤1 partial-line shape per window (recorded, inside
the threshold).

## 5. Layer truths (as-designed, confirmed as-operated in §3)

- **Two operation journals** (M4.7): CP controlplane.db `operations`
  (CamelCase statuses; terminal = Succeeded/Failed/Rejected/Cancelled/
  Stale/Conflict) and the agent Core authority's core.db `operations`
  (lowercase). Every soak cycle asserts both terminal for its VM.
- **Spawn-at-create** (M4.3/M4.7, `process.rs` create_vm): a converged
  create has EXACTLY ONE idle VMM (api-socket only, no payload until
  start) and provisions its tap; a failed create has neither but can
  leave a phantom CP row (#368) — the soak's create-timeout branch
  cleanup-deletes and the per-cycle residue assertions catch violations.
- **Taps** (M4.4/M4.7): provisioned at CREATE, removed ASYNCHRONOUSLY by
  delete (30 s settle), persistent across stop. The per-cycle tap
  assertion polls the settle window.
- **Delete convergence is physical-side** (M2.5): the BFF list/volume
  row/backing are RETAINED on delete — the soak asserts CH process gone,
  tap removed, stord session closed; the retention is disclosed once.
- **#345 wedge**: graceful stop of an adopted VM can leave the VMM alive
  with a dead API socket; the stop wait detects 3 dead-API strikes and
  remediates with SIGKILL (warn; the stop-latency record carries the
  flag). The soak VMs are NOT adopted (no agent restart in this
  scenario), so the wedge is not expected — the detection stays armed.
- **bytesTransferred resets past BULK_COPY** (M4.6/M4.7): migration
  throughput uses totalBytes / BULK_COPY-duration, never byte deltas
  across phase boundaries.
- **The stord DB resolves from the live daemon's argv** (#376): no daemon
  is killed in this scenario, but the session checks resolve the live
  stord's DB per call anyway (m4.7 convention).
- **Migration task state is in-memory** on the source stord; sessions
  hydrate from stord.db on restart (M4.6) — P5 uses one uninterrupted
  pair, so this only matters for the close-out session check.
- **The agent's `/metrics`** (metrics_server.rs) is a fixed node-scoped
  gauge set (~22 series measured, constant — §3; plus core-managed journal gauges) — the cardinality
  assertion keys on that shape.

## 6. Residual risk / not claimed

- **Everything scale-shaped is out**: the 4 readers / 2 writers / 6 cycles
  are bounded by THIS host (16 vCPU, 31 GiB, nested KVM, all daemons +
  guest co-resident). No concurrency, density, throughput or
  requests-per-second claim may be derived from the records; the numbers
  exist so future changes have a baseline to diff against.
- **Boot-time variance dominates the soak's wall-clock** (nested virt):
  cycle times will vary run to run; the latency distributions (not single
  numbers) are the record.
- **The read-latency fast path** (curl + the chvctl-stored JWT) measures
  the BFF HTTP surface, not the gRPC/agent path beneath it; chvctl-spawn
  overhead is excluded by design (disclosed in §2.2).
- **Idle-window DB/fd baselines are point-in-time**: taken after a 60 s
  settle at rest; slow background effects longer than the window would be
  missed (the P1→P3 comparison is the actual gate).
- **CP-orchestrated migration, host reboot, multi-node, #394
  concurrent-write migration, M2.5 retention**: out of scope as in
  M4.3–M4.7.
