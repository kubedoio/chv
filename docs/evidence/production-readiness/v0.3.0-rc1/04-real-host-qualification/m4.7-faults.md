## 1. Scope

The prompt-04 milestone §M4.7: fault & interruption matrix on real (nested)
KVM, reusing M2.4's fault shapes at the process level. Every leg kills a
service inside an operation's execution window and asserts the **forbidden
outcomes** never occur regardless of which side of the race window the death
landed on — never merely eventual success.

**Claimed (pending the live run):**
- **Mid-operation kills converge or fail cleanly, never wedge:** CP SIGKILLed
  mid-CreateVm dispatch (F1), agent SIGKILLed mid-StartVm CH-spawn (F2),
  stord SIGKILLed mid boot-volume provision (F3), nwd SIGKILLed mid
  tap-provision inside CreateVm (F4), source stord SIGKILLed mid-BULK_COPY
  (F5), CP SIGKILLed mid-BULK_COPY (F6). Each leg's outcome assertion is the
  disjunction *converged OR terminally-failed-cleanly*; only an eternal
  non-terminal op (beyond the CP reaper's 120 s recycle + settle window) is
  an error. A terminally-FAILED op is the #368 fail-closed truth: a PASS with
  a disclosure warning.
- **No duplicate processes:** ≤1 cloud-hypervisor process per VM and globally
  exactly the number of Running VMs after every leg; exactly one stord and
  one nwd after an agent restart (the supervisor must *adopt* the living
  daemons via their sockets — `supervisor.rs` skips spawn when the socket
  accepts — never double-spawn).
- **No lost/duplicated authoritative state:** CP volume row ↔ physical
  backing bijection for live VMs (deleted VMs are the documented M2.5
  retention class — warned, not gated); exactly one CreateVm op row per
  created VM no matter how many dispatches replay across a CP restart; every
  journaled op terminal in BOTH journals (controlplane.db CamelCase +
  core.db lowercase) after each leg; unrelated VMs' op histories unchanged.
- **No orphaned disks/taps:** tap count returns to the expected baseline
  after every delete (taps are provisioned at CREATE — `attach_vm_nic` runs
  inside the agent's CreateVm dispatch — and removed *asynchronously* by
  delete, M4.4's 30 s settle); no physical volume backing without a CP row;
  no stord session without its volume; live stord sessions all closed at the
  final sweep.
- **Migration interruption from the source side** (extends M4.6 N9, which
  killed the destination): source death mid-BULK_COPY leaves no zombie task
  after restart (in-memory registry), the destination partial receiving
  volume is RETAINED (create_new), the documented recovery (restart source →
  hit the create_new refusal → remove the partial → re-trigger) completes
  with digest + byte-compare verification.
- **CP loss mid-migration is survivable by design:** the stord↔stord path is
  direct (M4.6 declaration), so the transfer keeps advancing through the CP
  outage, completes with digest verification, and the CP journals no
  duplicate/phantom work across its restart.
- **Idempotent cleanup:** second delete of the same VM → clean not-found or
  idempotent success, never a crash-class (5xx) error; stop of an
  already-stopped VM → clean; delete of a VM whose create is still in flight
  → converges to absence with no orphaned disk/tap.

**Not claimed (§6):** the CP-orchestrated migration path (out of scope per
M4.6 — fails closed in core-managed mode by design); host reboot (M4.3's
recorded not-provable subset); multi-node anything; the BFF/CP row retention
on VM delete (the documented M2.5 deferred scope — recorded, not gated,
exactly as in M4.3 Leg F / M4.5 Leg E); concurrent-writer migration (#394,
M4.6's boundary).

## 2. Harness

Same deploy shape as M4.3–M4.6 (`deploy.sh --exec`). The scenario adds the
M4.6 two-standalone-stord mTLS topology for F5/F6 (deliberately **not**
agent-supervised, #385), with the same pinned-and-verified grpcurl
v1.9.3 provisioning (checked-in checksums asset) and a 4 GiB patterned seed
(1024 × 4 MiB chunks) so BULK_COPY lives long enough to kill inside.

**The M4.7 delta vs. the prior milestones:** every kill targets an operation
*in flight*. Each leg polls tightly (0.2 s) for the op to be claimed (CP
journal status `Running` = dispatch executing right now) or for the host
effect to start (the boot-volume backing file appearing), then SIGKILLs
inside the window. If the window is missed, the kill still happens and the
assertions are unchanged — both sides of every race are acceptable outcomes
and every assertion is written as "converges OR fails cleanly".

One base VM (create → start → boot to logind, so later stops are ACPI-safe —
the M2.5 run-8 lesson) is reused by several legs; the F2 leg boots a second
VM for the same reason; every other leg only creates (no boot), keeping the
run inside the ~25 min budget (boot waits dominate).

| Leg | Kill | Window | Recovery asserted |
|-----|------|--------|-------------------|
| F1 | CP SIGKILL | CreateVm op claimed (journal `Running`) | op terminal (Succeeded or Failed — #368 disjunction), retry create converges on the restarted CP, deferred agent reports drained (#343 gate) |
| F2 | agent SIGKILL | StartVm op claimed (CH spawn in flight) | base VM's CH survives (separate process); restarted supervisor *adopts* the living stord/nwd (exactly one each); VM Running or cleanly-failed; retry start → Running; boot evidence for F7's later stop |
| F3 | stord SIGKILL | boot-volume backing starts materializing (the M4.5-proven multi-second seed-conversion window) | supervisor respawn (#376: the respawned daemon's config/DB resolves from its argv — agent runtime_dir, not the deploy dir); provision converges or fails cleanly; retry converges through the respawned stord; session closed on delete (the detach/delete contract for this topology) |
| F4 | nwd SIGKILL | CreateVm op claimed (tap provision runs inside the create) | supervisor respawn; create converges or fails cleanly; **no orphaned tap** once the leg settles; retry converges |
| F5 | source stord SIGKILL | BULK_COPY observed (0.2 s poll) | no zombie task after restart; destination partial RETAINED; create_new refusal on re-trigger; documented recovery → COMPLETED + digest |
| F6 | CP SIGKILL | BULK_COPY observed | transfer keeps advancing while the CP is down (two bytesTransferred samples); completes across the restart; CP op set unchanged (no phantom journal work) |
| F7 | — (no kill) | — | idempotent cleanup: delete → re-delete (never crash-class), stop → re-stop, delete-vs-in-flight-create; final global sweep: zero CH processes, zero scenario taps, row↔backing bijection, live stord sessions closed, every journaled op terminal, one CreateVm row per VM |

**Deviations from the plan's leg list (disclosed):**
- *F3 (storage provider mid-provision):* no standalone volume
  create/attach API exists on a core-managed node — the `attach_volume` /
  `detach_volume` RPCs fail closed there
  (`crates/chv-agent-core/src/agent_server.rs:1344,1402`, "unsupported in
  core-managed mode"). The only operator-reachable volume path is the
  boot-volume provision inside a fresh VM create, so F3 kills stord during
  exactly that. "detachable/deletable afterwards" maps to the
  session-close-on-delete contract proven in M4.5.
- *F5 (source-side migration kill):* the plan's "migration interruption" is
  satisfied from the source direction — M4.6 N9 already proved the
  destination side on the same topology.

## 4. Findings

Filed from the live runs (product findings become issues, never fixes inside
the scenario PR — campaign rule):

- **[#405] VM delete after an agent restart leaked host taps and volume
  sessions** (run 1, F7 — `tap-c4f4aed3`/`tap-027c51ae` survived two HTTP-200
  deletes through the final sweep): the legacy-core delete path's only
  side-effect source is the in-memory `VmRuntime` map, which dies with the
  agent process; the M2.2a "documented crash residual" fires on ordinary
  restarts, not just crashes. **Fixed by #407** (fallback drain from the
  restart-durable NodeCache observed-attachment source) — **validated live in
  run 2**: F7's base/f2 tap removal, the final-sweep zero-tap and
  zero-session assertions all pass, and the agent log shows the fallback
  firing (`draining stord/nwd handles from durable observed attachments
  (post-restart fallback)`).
- **[#406] Retried `vm delete` of a retained VM returned HTTP 500** (run 1,
  F7): the BFF's per-VM idempotency keys were plain UNIQUE INSERTs colliding
  with M2.5 retention. **Fixed by #408** (pre-mutation replay inside the
  existing `BEGIN IMMEDIATE` tx, args-hashed resize key, `recorded_status`
  disclosed on replay) — **validated live in run 2**: F7's second delete
  returns idempotent success (HTTP 200).
- **[#368] reproduced with a storage-side trigger** (run 1 F3, run 2 F3/F4 —
  classification `failed_368`): CP `CreateVm:Succeeded` (submit-level) while
  the core effect terminally failed — phantom VM row, no observed state, no
  physical volume, no re-drive. Not new (filed by M4.4 with an nwd-side
  trigger); the M4.7 reproduction extends the trigger set to stord and nwd
  deaths and is recorded as a comment on #368. The scenario discloses it as a
  warn per leg and proves the recovery paths (cleanup-delete works; the retry
  create converges on the respawned daemon).
- **[#409] Agent death inside the guest firmware boot window wedges the VM
  half-booted forever while everything reports Running** (run 2, F2): the
  kill landed between the payload push/vm.start and the kernel banner; the
  guest console froze at 428 bytes mid-PCI-enumeration, no kernel ever
  printed (420 s banner timeout), the restarted agent adopted the VM
    ("console capture resumed"), the re-driven start correctly no-op'd on
  CH's `Running`, and the later graceful stop could never succeed (no OS) —
  force-stop only. Prime suspect (by elimination — everything else in the
  boot path is VMM-owned): the serial-socket path. Fix in flight; the leg
  stays a hard assertion.
- **F3's fail-closed attach surface** (recorded as the leg's deviation, not a
  finding): core-managed mode has no standalone volume attach/detach — see
  §2.

## 5. Layer truths (as-designed, to be confirmed as-operated)

- **Two operation journals:** the CP's controlplane.db `operations` table
  (CamelCase statuses; terminal = Succeeded/Failed/Rejected/Cancelled/Stale/
  Conflict per `chv-controlplane-types/src/domain.rs`; non-terminal adds
  AwaitingOperatorInput) and the agent Core authority's core.db `operations`
  (lowercase statuses: accepted/running/succeeded/failed/unsupported). A
  dispatch failure marks the CP op Failed immediately (the orchestrator's
  Err branch — AGENT_REJECTED); a CP death mid-dispatch leaves the op
  Running until the reaper recycles it (CreateVm class: 120 s → Accepted),
  hence the 300 s op-settle window.
- **Supervisor adoption:** on agent restart the supervisor checks socket
  liveness before spawning (`supervisor.rs`: "external daemon already
  listening; skipping spawn") — living daemons are adopted, so an agent
  crash+restart can never double-spawn stord/nwd. A respawned daemon gets a
  generated config at `${agent runtime_dir}/chv-stord.toml` with the SAME
  socket path (from the agent's config) but a different runtime_dir — its
  stord.db is therefore NOT the deploy stord's DB (#376; the scenario
  resolves the live daemon's DB from its argv per call).
- **Taps:** provisioned at VM CREATE (`attach_vm_nic` inside the CreateVm
  dispatch — `reconcile.rs`/`agent_server.rs`), named `tap-<8 hex>`
  (`chv-nwd-core/src/executor.rs`), removed ASYNCHRONOUSLY by delete
  (M4.4: 30 s poll), and persistent across VM stop (carrier drop only).
- **Disk inventory:** no stord volume-inventory RPC exists (only
  ListVolumeSessions); physical volumes are `vms/<vm_id>/<volume_id>.img`
  (absolute locators from `prepare_vm_resources`); CP volume rows live in
  the `volumes`/`volume_desired_state` tables (controlplane.db). The
  row↔backing bijection is therefore checked host-side by the scenario.
- **M2.5 retention truth:** on VM delete the BFF list/volume row/backing are
  RETAINED (authority-side delete; M4.5's final run recorded it as 2
  warnings) — absence checks use honest disjunctions (pass or retention
  warn) and deleted VMs are excluded from the row↔backing check.
- **Migration task state is in-memory** (M4.6): a restarted source stord
  serves nothing for a killed migration_id — `GetDiskMigrationStatus`
  answers 200-OK with result NotFound / "migration not found" (the response
  still carries a `phase` field, so the no-zombie check keys on the
  not-found marker). Sessions hydrate from stord.db on restart
  (`chv-stord-core/src/server.rs`), and the LocalFileBackend's health and
  volume_size are stateless (path derived from the handle), so an
  old-handle re-trigger after a same-config restart should work — the
  scenario asserts the disjunction (hydrated-handle pass OR re-open branch
  with a warn and an equivalent pass).
- **#343 gate:** an agent restart with unflushed deferred control-plane
  reports bricks the node (startup fails closed on the retained NodeCache),
  so after every CP kill the deferred-report queue is drained to zero
  BEFORE any agent restart (F1 → F2 ordering).
- **#345 wedge:** after a graceful stop of an adopted VM the VMM can stay
  alive with a DEAD API socket while the stop loop reports success — the
  stop wait detects 3 consecutive dead-API strikes and remediates with
  SIGKILL (M4.3/M4.5-proven; lifted verbatim).

## 6. Residual risk / not claimed

- **Every kill is a race** (by design): if a claim window is missed the kill
  lands post-convergence — the leg's assertions are unchanged and the
  miss is disclosed as a warn, but the mid-flight evidence for that leg is
  weaker. BULK_COPY windows are the most reliable (multi-second); the
  CreateVm/StartVm claim windows depend on dispatch timing.
- **F6's "no phantom CP work" check** compares the full operations-table
  fingerprint across the CP restart — any legitimate background journaling
  during the window would trip it and be disclosed live.
- **CP-orchestrated migration, host reboot, multi-node:** out of scope
  (§1/§2; M4.6 declaration and M4.3's recorded subset).
- **M2.5 delete retention:** rows/backings of deleted VMs persist by design
  — recorded as warnings, never gated; the final sweep's bijection check
  therefore asserts physical→row only (retained backings keep their rows).
- **#394 concurrent-write migration boundary** (M4.6 §4.1) applies to F5/F6
  as well: quiescent seeded volumes only.
