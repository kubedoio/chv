# Prompt 01 — Network Isolation and Host-Safety Gate

Resolve the production isolation risk tracked by #227 or its current successor.

## Preconditions

- Execute Prompt 00 first.
- Re-read current `crates/chv-nwd-core` firewall/executor/reconcile code.
- Revalidate #227 and any related PR against current `main`.
- Work on a dedicated implementation branch from the current campaign baseline.

## Goal

Make CHV default-deny policy apply **inside the CHV-owned guest traffic boundary**, never as a host-wide default-drop policy.

CHV must be able to enforce tenant/guest policy without changing the behavior of unrelated host, container, Kubernetes/CNI, Docker, routing, or forwarded traffic.

## Required design invariant

The intended boundary is conceptually:

```text
host nftables hooks: accept
        |
        +-- unrelated traffic ------------------> unaffected
        |
        '-- CHV-owned bridge/TAP/topology ------> CHV policy chains
                                                   |
                                                   '-- default deny
```

Interface/topology ownership is authoritative. Subnet-only inference is not sufficient.

## Required work

### 1. Current-state proof

Before editing, capture the exact current behavior:

- nftables tables/chains/hooks generated by CHV;
- base-chain policy;
- how topologies, bridges, TAPs, VM NICs, and rules are named/owned;
- whether reconciliation flushes or replaces shared state;
- current behavior when ownership metadata is missing;
- current identifier validation.

Preserve a before-state regression test that demonstrates the unsafe host-wide effect if it is still present.

### 2. Scope policy to CHV-owned traffic

Implement a design in which:

- base hook chains do not impose a host-wide drop policy;
- CHV-owned traffic is explicitly dispatched to CHV policy chains;
- forwarding paths used by VM traffic are covered;
- topology A cannot affect topology B;
- unrelated nftables tables/chains/rules remain untouched;
- delete/reconcile removes only objects owned by the target topology;
- missing/ambiguous ownership fails the requested CHV policy operation rather than guessing.

### 3. Input and privilege safety

Validate every user-derived or topology-derived identifier before command execution.

Do not create:

- arbitrary nftables expression injection;
- arbitrary command execution;
- host-global flush behavior;
- fallback to an unverified host interface.

### 4. Tests

At minimum add privileged integration coverage for:

- empty CHV policy while SSH-equivalent host namespace traffic continues;
- host egress/DNS-equivalent traffic continues;
- unrelated veth forwarding continues;
- a second independent CHV topology is unaffected;
- CHV guest traffic defaults to deny when no allow rule matches;
- explicit allow rules work on the real forwarding path;
- repeated reconcile is idempotent;
- deleting one topology removes only its own policy objects;
- invalid identifiers fail before mutation;
- missing topology/interface ownership fails closed.

Where a Kubernetes-capable disposable worker is available, add or preserve a test proving CHV policy does not alter CNI connectivity. If that environment is not available, do not claim Kubernetes coexistence as qualified.

### 5. Observability

Expose enough bounded diagnostics to answer:

- which topology owns a policy object;
- which interface caused dispatch into CHV policy;
- why a packet class is expected to be denied/allowed;
- whether reconciliation failed before mutation.

Do not add unbounded per-packet logging or unbounded metric labels.

## Acceptance criteria

- #227's current acceptance criteria are satisfied or explicitly superseded by stronger reviewed criteria.
- No CHV policy path installs host-global default-drop behavior.
- Unrelated host/network-namespace traffic remains functional in privileged tests.
- CHV guest default-deny remains effective.
- Ownership and cleanup are deterministic and idempotent.
- The exact implementation commit has KVM/Linux-host evidence.
- Documentation states the qualified coexistence profile and limitations.

## Forbidden outcomes

- weakening guest default-deny to make host tests pass;
- disabling CHV firewall by default as the "fix";
- relying only on subnet matching;
- flushing the full host ruleset;
- claiming Kubernetes/Docker coexistence without corresponding evidence;
- replacing `chv-nwd` with a new networking service.

## Exit gate

Prompt 01 passes only when CHV policy is demonstrably confined to CHV-owned guest traffic on a real Linux host and unrelated networking survives apply, reapply, and delete operations.
