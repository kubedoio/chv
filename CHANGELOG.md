## [Unreleased]

### Added
- **Control plane / agent (node authority mode — issue #378)**: the control plane now knows each node's authority mode. The agent reports its `authority_mode` config value (a static per-process fact: `legacy`, `core-managed`, or `core-native`) as a typed `NodeInventory` proto field (`AuthorityMode` enum) at enrollment and on every ~30 s periodic inventory cycle, and the control plane persists it on a new nullable `node_inventory.authority_mode` column (migration `0057`; no backfill — existing rows stay NULL). The mode is consumed by the accept-time volume-op rejection below. Fail-open by construction: an unreported/NULL/unknown mode never changes any behavior — the agent's fail-closed dispatch remains the single-writer enforcement, and this carrier is observability/policy input only. An unspecified re-report never wipes an established mode (the upsert COALESCEs like the version columns); a mode flip at agent restart overwrites on the next report. Design writeup: [`docs/design/issue-378-accept-time-volume-op-rejection.md`](docs/design/issue-378-accept-time-volume-op-rejection.md).
- **Control plane (credential encryption key-source observability — issue #336)**: startup logging now says which secret the S3 credential cipher was keyed from. A dedicated `CHV_ENCRYPTION_KEY` logs an info line; the legacy `CHV_JWT_SECRET` fallback — reached only by pre-#335 hosts and env-driven deployments without `/etc/chv/encryption.env`, since both install surfaces (`install.sh` and the package postinst) mint a dedicated key — now logs a startup **warning** stating plainly that S3 credentials are being encrypted under the JWT signing secret, that rotating `CHV_JWT_SECRET` will invalidate all stored S3 credentials (fail-closed `AuthFailed`, re-entry required), and pointing at the DR runbook for migrating to a dedicated key. Previously the fallback was completely silent at startup, and a routine JWT-secret rotation surfaced later as opaque S3 auth failures. The DR runbook (`docs/runbooks/control-plane-dr.md`) now documents how to restore or mint the dedicated key on a replacement host, and the fallback's rotation hazard with a zero-re-entry migration (copy the current `CHV_JWT_SECRET` value into `/etc/chv/encryption.env`, then rotate the JWT secret freely). Encryption behavior is unchanged — same key derivation, same ciphertexts, same fallback semantics, no new config knobs; only log lines and documentation are new. Whether to drop the fallback entirely remains a maintainer decision tracked in #336.

### Changed
- **Control plane (behavior change — Unimplemented dispatch fast-fail, issue #378 §7 follow-up)**: the orchestrator's dispatch-retry machinery no longer retries an operation whose dispatch was refused with gRPC `UNIMPLEMENTED` — it now fails terminally on the first dispatch. Previously every error class was retried identically on the 10/20/40 s backoff curve (4 attempts, ~70 s): for `Unimplemented` — terminal-class by definition, since a verbatim retry can never succeed unless the agent binary changes — this produced ~70 s of retry noise before an opaque `Failed/DISPATCH_FAILED` with the agent's clear refusal text buried in the exhaustion message. The node client now preserves the error's identity (`ChvError::Unimplemented`, a typed variant — no status-text string-matching) instead of flattening every tonic status to `Internal`, and the tick handler bypasses its retry arm for that class so the terminal `Failed` row written at dispatch time (`error_code: UNSUPPORTED_BY_AGENT`, carrying the agent's own refusal message, e.g. "snapshot_volume is unsupported in core-managed mode") is never resurrected to `RetryPending` by `mark_for_retry`. **Blast radius, disclosed**: this applies to every `Unimplemented` dispatch (~25 refused legacy RPCs behind the Core authority — the four volume surfaces of #495 plus VM snapshot/restore, resize, attach/detach, coredump, overlay, and the rest), not just volume ops; terminal-class handling is universally correct for `UNIMPLEMENTED`, which is the approved design. Affected surfaces now reach `Failed/UNSUPPORTED_BY_AGENT` immediately instead of after retry exhaustion; other error classes (`Unavailable`, `DeadlineExceeded`, `Internal`, transport) retry byte-for-byte as before, and the agent-side fail-closed enforcement is untouched (this is retry-machinery only). Version-skew note: no current RPC produces a transient `Unimplemented` (all current producers are static fail-closed gates; recent contract growth was additive fields, not new methods), but a future CP dispatching a genuinely new RPC to a not-yet-upgraded agent during a rolling upgrade would now fail fast instead of retrying into success — the 10/20/40 s curve cannot bridge a rollout window anyway; the operator re-issues after the upgrade. One deliberate convention, disclosed: a `MigrateVm` dispatch refused with `Unimplemented` lands terminal under the migration arm's own code — `MIGRATION_FAILED`, not `UNSUPPORTED_BY_AGENT` — with the agent's refusal text carried in `error_message` (same `unimplemented: …` Display rendering as the single-node surface — only the terminal code differs); the migration path keeps its terminal-code convention and only shares the tick's retry-bypass. Design writeup §7: [`docs/design/issue-378-accept-time-volume-op-rejection.md`](docs/design/issue-378-accept-time-volume-op-rejection.md). Refs #378.
- **Control plane (behavior change — issue #378)**: volume snapshot, restore-snapshot, delete-snapshot, and clone against a **core-managed** node are now rejected at accept time with `InvalidArgument` (HTTP 400 through the BFF, message "volume snapshot/restore/snapshot deletion/clone is not supported on core-managed nodes") instead of being accepted with HTTP 200 and then failing ~70 s later after the orchestrator's dispatch retries exhaust against the agent's fail-closed `Unimplemented`. The check runs in the CP lifecycle BEFORE any journaling — a rejected request leaves no `operations` row, no `volume_desired_state` intent, and (clone) no phantom target volume row — and uses the same node resolution the dispatch uses (the volume's node; for clone, the source's placement node). Legacy-mode and unreported-mode (NULL) nodes are byte-for-byte unchanged (fail-open; the rejection fires only on a definite `core-managed` report). **Behavior change, disclosed**: automation that previously parsed the 200 "accepted" response from these four surfaces on core-managed nodes now gets an immediate 400 — that is the fix (the 200 was a lie; the op always failed), but scripts keying on the old shape will see the difference. chvctl surfaces the 400 message through its existing error path. In-flight ops accepted before the fix run the old bounded retry path to `Failed/DISPATCH_FAILED`; pre-existing journaled `snapshot_op` intents are untouched (flagged in the design doc's residual risks). The `Unimplemented` fast-fail in the orchestrator retry machinery (stop retrying refused RPCs for every surface) is deliberately NOT included — separate follow-up, wider blast radius (~25 refused RPCs), tracked in the design doc §7. (#378)
- **Storage (stord, behavior change — migration TLS accept-loop hardening, follow-up to #402/#479)**: the migration receiver's chv-owned TLS accept loop now bounds how long a connection may sit in its handshake. An accepted TCP connection that never sends a ClientHello used to pin one spawned handshake task plus its file descriptor forever, and the exposure scales linearly with connection count (slow-loris on the migration port); the loop now closes such connections after a fixed 30 s handshake timeout. **Behavior change, disclosed**: an idle migration-port connection is now closed after 30 s instead of hanging open — tonic's internal handshake path (which this loop replaced in #479) had no timeout either, so this is parity hardening of a loop chv now owns, not a regression, and it only observes and closes: a legitimate handshake is a handful of round trips over an already-established TCP connection (loopback proof tests complete in single-digit milliseconds), so the timeout never fires for a real peer. The timeout is logged at info level with the peer address and nothing more (`migration TLS handshake timed out; closing connection`), deliberately below the warn level of an mTLS rejection — a peer that never started a handshake was not rejected by policy. It is a named constant, not a config knob: there is no operational tuning story (30 s is orders of magnitude above any legitimate completion time), and the loopback tests exercise the behavior through a duration-parameterized test seam instead. Also new observability: a handshake that completes *after* the server was shut down (shutdown raced a completing handshake) now logs at debug level (`migration TLS handshake completed after server shutdown; connection dropped`) instead of dropping the finished stream silently, so an operator can tell a raced shutdown apart from an mTLS rejection. mTLS enforcement is untouched — same mandatory `WebPkiClientVerifier`, no `allow_unauthenticated()`, rejected-handshake warn lines unchanged in content and level; the timeout and the debug line only observe and close, never admit. New tests pin all four behaviors: the sender-abort rejection leg (`received fatal alert: UnknownCA` — the exact rustls 0.23 rendering the #402 changelog documents, previously asserted nowhere), the timeout closing a silent connection (with a positive leg proving legitimate handshakes complete under the same shortened timeout), the shutdown-race debug line, and >64-concurrent-handshake + mid-handshake-disconnect churn (no drop, no wedge, every disconnect observed exactly once). (#479 follow-up)
- **Storage (stord, behavior change — issue #401)**: a destination-only stord is now expressible. Previously `migration.enabled = true` made the *client* identity mandatory (`client_cert_path`, `client_key_path`, `ca_cert_path`, `dest_server_name` all required), so a stord that should only ever *receive* migrations could not be configured without minting and maintaining a client identity it would never use (found in the M4.6 qualification, which carried an unused client identity as a workaround). The two migration halves are now independently optional under `enabled = true`: omitting all four client fields configures a destination-only stord whose outbound migration actions fail with the sender's existing `failed_precondition` error (unchanged no-plaintext-fallback behavior); omitting all receiver fields keeps the existing source-only stord. Each half remains all-or-nothing within itself (a partial half is still a startup error), `enabled = false` with any field anywhere in the section is still a startup error (#393/#395 semantics), and `enabled = true` with *neither* half configured is a new startup error — an enabled migration section that configures nothing is a misconfiguration, previously masked by the client-fields requirement. Behavior change boundary: the only configs whose outcome changes are ones that are startup errors today (destination-only) and now start; nothing that starts today stops starting — source-only, both-halves, disabled-clean, and all error cases (partial halves, `enabled = false` contradictions, unreadable/invalid/mismatched material) are byte-for-byte the same validation paths. Operators wanting a destination-only stord: set `enabled = true` plus the four receiver fields and drop the client identity entirely (example in `docs/examples/stord.toml`).

### Fixed
- **Control plane (docs — issue #384 follow-up)**: re-anchored the #384 design doc's writer-census line refs at the #501 merge commit (that merge's own insertions had shifted them; the clone-path rows now cite the as-built `materialize_clone_target` locations), and corrected this section's #384 entry: the vtep fabric-IP 409 reclassification surfaces through `enroll_node` and `report_node_inventory` only — fabric-plan compile flattens its errors to `Internal` regardless of class. Documentation only; no code change. (#384)
- **Agent (stord respawn config fidelity — issue #385)**: the agent supervisor's respawn of a dead stord no longer silently discards the operator's `stord.toml` keys. The generated respawn config carried only `socket_path`, `runtime_dir` (the **agent's** dir, not the operator's), a hardcoded `log_level`, and — since #377 — `path_allowlist`: everything else the operator configured was dropped on respawn, including `backend_type` (an LVM/iscsi/ceph deployment respawned as the `local` backend — a daemon that reports healthy on the socket while serving the wrong backend and data location), `device_allowlist` (fail-open to allow-all device paths), `backend_allowlist`, `migration_dest_allowlist`, and the `[migration]` block (inbound receiver listener silently disappears), plus the recorded `stord.db`/snapshot `runtime_dir` relocation trap. Fix, opt-in: new `AgentConfig.stord_config_path` (`Option<PathBuf>`, default `None` = today's generated-config behavior byte-exactly). When set, the supervisor execs `chv-stord <operator-config-path>` directly — no config generated, every operator key (and every future key) survives respawn by construction; the supervisor validates only that the file is readable, parses as a `StordConfig`, and its `socket_path` matches the agent's `stord_socket`. On ANY validation failure (missing file, parse error, socket mismatch — the mismatch fallback is mandatory: a stord bound elsewhere would wedge the agent's health check forever) it emits a loud warn naming the reason and takes today's generated-config path unchanged, so validation failures are never worse than status quo. A config that *validates* but fails at daemon startup (a missing/unwritable `runtime_dir` parent — stord aborts opening its session store; a bad backend constructor; migration TLS material checked at startup, not parse time) is a different case, disclosed in `docs/OPERATIONS.md`: the supervisor re-validates the file (it still passes), re-execs the operator path under its restart throttle, and never falls back to the generated config — the same posture as systemd `Restart=on-failure` restarting the same broken file, with the same remedy (fix the operator config); the health check is never wedged. The health check and the rest of the supervisor lifecycle are untouched, and the nwd spawn path is deliberately unchanged (tracked as #504). `install.sh` now sets `stord_config_path` for standard installs (it writes `/etc/chv/stord.toml` itself with a matching socket and grants the agent user group-read via the `chv-stord` group); hand-managed deployments set the key per `docs/examples/agent.toml` and `docs/OPERATIONS.md`. Security posture unchanged: `stord.toml` was always an operator-controlled, root-owned file (`root:chv-stord 0640`), and the pass-through is the same trust boundary as systemd's existing `ExecStart=/usr/bin/chv-stord /etc/chv/stord.toml` — the agent merely takes over systemd's role for the crash window (does not weaken #376/#377; the supervisor reads the file using the install-time group read grant). Design writeup: [`docs/design/issue-385-stord-respawn-config-fidelity.md`](docs/design/issue-385-stord-respawn-config-fidelity.md) §6.1. (#385)
- **Control plane (clone target TOCTOU — issue #384)**: `clone_volume`'s target materialization no longer races. The accept-time target-absence check and the target write used to be two separate steps around the general `upsert_volume` (`ON CONFLICT DO UPDATE` — the physical `volumes` row has no generation guard): two concurrent clones onto the same caller-supplied target id (the only volume-id class with no randomness protecting it — the BFF forwards the request body's `target_volume_id`, and the BFF's per-request idempotency keys do not dedupe concurrent clones) could both pass the check, both journal and accept operations, and both dispatch to the agent, with the physical row last-writer-wins and two live conflicting operations on one target; separately, a resize of the clone SOURCE committing between the shaping read and the write silently gave the target a stale capacity. The store now has `materialize_clone_target`: one `BEGIN IMMEDIATE` transaction that reads the source row under the write lock (the read can no longer split from the target write — closing the clone's exposure to the resize executor's direct `UPDATE volumes SET capacity_bytes`, the only unguarded physical-table writer), strictly inserts the target (`ON CONFLICT DO NOTHING` + rows-affected, so a concurrent same-target materialization fails closed instead of overwriting the winner's shape), and writes the generation-guarded `volume_desired_state` intent row in the same transaction. **Error contract, disclosed**: the race loser gets the Conflict class — gRPC `ALREADY_EXISTS`, HTTP 409 through the BFF's already-mapped `Conflict → BffError::Conflict` arm (the store→service `From` mapping for `StoreError::Conflict` is new) — while the accept-time pre-check keeps its `InvalidArgument`/400 "target volume id already exists"; the two paths are now distinguishable in logs, and the race loser's journaled operation is marked `Failed/INTENT_PERSISTENCE_FAILED` instead of being left Accepted. The new `StoreError::Conflict` arm is not clone-scoped, disclosed: the pre-existing vtep fabric-IP conflict (a registration losing repeated races in the `100.100.0.0/16` pool, `store/vtep.rs`) now also surfaces as `ALREADY_EXISTS`/409 instead of the old `Internal`/500 across `enroll_node` and `report_node_inventory` (the only production paths that surface the vtep conflict — fabric-plan compile flattens its errors to `Internal` regardless of class) — a classification improvement (a well-formed, retry-able report no longer renders as a server fault), disclosed here. **Idempotent replay, disclosed**: a direct gRPC caller repeating `meta.operation_id` re-runs the intent persist (the BFF and chvctl never set one), which with a strict insert would collide with its own earlier materialization — the operation receipt now carries a `created` flag (`create_or_get`'s insert rows-affected), and a replay whose existing target row matches this operation's shape is an idempotent success (same operation id acked, no row rewritten, nothing re-dispatched); a replay-eligible request skips the target-absence pre-check (on replay the target legitimately exists — this operation materialized it), so a first-time request carrying an `operation_id` against an existing target now gets 409 with a journaled Failed op instead of the pre-check's 400 with no residue — every existing client sends an empty `operation_id` and keeps the 400 path unchanged. Residual, disclosed: replaying a Conflict-failed operation with the same caller-supplied `operation_id` re-runs `accept_operation` — the #378 §7 terminal-replay quirk (a `Failed` journal row is resurrected to `Accepted` and re-dispatched), newly reachable for the clone residue; see the design doc's residual risks (§8). The general physical-row generation guard (the issue's broader finding) is deliberately deferred by maintainer decision with named reopen triggers (a new direct physical-table writer; a writer decoupling from the desired-state transaction; demonstrated physical-row corruption) — design writeup: [`docs/design/issue-384-physical-table-generation-guard.md`](docs/design/issue-384-physical-table-generation-guard.md) §6.1. No other writer changed: `upsert_volume`, the agent fragment-reconcile path, and the resize executor are untouched. (#384)
- **Control plane (overlay fan-out fast-fail — second-pass review of #500, issue #378 §7 follow-up)**: documentation and ordering hygiene on the merged all-refusals fan-out path, no behavior change. The `OverlayManager` type doc still described the pre-#500 contract ("individual node failures … do not fail the overall operation") and so actively contradicted the merged terminal path; it now states the real contract (mixed per-node failures aggregate as `Internal` and stay on the shared retry curve, corrected by the next plan dispatch; an all-`Unimplemented` fan-out — including the partial-success shape where some nodes applied their plan and only the failing nodes refused — fails terminally `Failed`/`UNSUPPORTED_BY_AGENT` on the first dispatch, no re-dispatch). The all-refusals roll-up message no longer reads as "all participants refused" in that partial-success shape — it now says "refused by all N failing node(s)" (nothing grepped the old wording: no test, orchestrator assertion, or qualification script matches it — the orchestrator tests assert on the agents' own refusal text, which rides the message verbatim either way). And the "deterministic fan-out order" claim behind the roll-up is now formally true instead of relying on SQLite's unordered scan: `get_fabric_peers_for_network` gained `ORDER BY node_id` (matching the store's house ordering for node lists), pinning the fabric-plan compile order and therefore the roll-up output; a new store test seeds peers in non-sorted registration order and asserts the flood list comes back in `node_id` order. (#378)
- **Control plane (Unimplemented fast-fail — overlay fan-out leg, follow-up to #498 / issue #378 §7)**: the `UpdateOverlay` fabric fan-out now preserves the `Unimplemented` identity when every per-node failure is a refusal, closing the one surface #498's fast-fail did not actually cover despite its "applies to every Unimplemented dispatch" disclosure. `OverlayManager::send_fabric_update` aggregated all per-node dispatch failures into a fresh `Internal`, erasing the refusal identity before the tick handler could classify it, and `dispatch_update_overlay` had no error arm writing terminal rows — so an `UpdateOverlay` against an all-core-managed cluster (every node's agent answering `UNIMPLEMENTED` with "update_overlay is unsupported in core-managed mode") still ran the full 10/20/40 s retry curve to an opaque `Failed/DISPATCH_FAILED` (~70 s of noise for an operation that could never succeed). Now: when the fan-out's failures are ALL `Unimplemented` refusals, the aggregation returns one `Unimplemented` carrying the deterministic per-node roll-up (fan-out order), and `dispatch_update_overlay` gained the terminal-write arm mirroring the single-node dispatch path — `Failed` / `UNSUPPORTED_BY_AGENT` with the agents' refusal text on the FIRST dispatch, zero retries, no `mark_for_retry` resurrection, and the same flatten-to-`Internal` convention if the terminal write itself fails. Mixed fan-out failures (some refusals, some other error classes) are deliberately unchanged: they keep today's `Internal` aggregation and retry curve, because a partial refusal is not terminal-class for the operation — the non-refusing nodes may succeed on retry. The #498 CHANGELOG disclosure's blanket claim is now accurate. Design doc §7/§12 status markers corrected and the as-built record extended; the volume-restore runbook's Path A now notes the core-managed accept-time 400. (#378)
- **Control plane / agent (zombie VMs — issue #368)**: a VM create whose Core effect terminally failed on the agent (e.g. a transient stord/nwd backend failure during the create) left the VM desired-but-never-created forever — the dispatch had already acked ok, so the convergence loop never revisited it, and the CP UI showed the desired power state as if the VM existed. Fixed with four coordinated pieces and no proto change. **C1 (Core re-drive primitive)**: the Core store gains `requeue_failed_create` — a CAS on the live `vms` row requiring the VM's latest create operation to be terminally `failed`, which derives a canonical create envelope from the live row and inserts a NEW `CreateVm`-kind operation so the existing effector simply re-executes it (failed operations stay terminal: a re-drive is always a new operation, never a resurrection; VM ids are never reused across specs; every journal mutation stays inside the executor's single-writer claim path), plus a claim-time fence: a requeued create claimed against a tombstoned (operator-deleted) VM persists terminal `Failed` with code `VM_TOMBSTONED` in the same transaction and never runs. **P1 (agent telemetry)**: the agent's existing `VmStateReport` loop reports terminally-failed creates as `runtime_status = 'Failed'` carrying the public-safe Core failure code. **P2 (CP re-drive loop)**: the orchestrator tick runs a bounded re-drive pass gated on the desired state still demanding the VM (an operator delete stops the loop) and on no incomplete create-family operation in flight (a crashed re-drive holds the gate closed until restart classification resolves it as `InspectRequired`), re-issuing the create as a new `RecreateVm` operation at the original create's generation, spaced by the existing dispatch-retry backoff curve (10 s / 20 s / 40 s, at most 3 attempts, no new config knobs). **P3 (visible failure)**: on exhaustion the VM is marked terminally `Failed` with `CREATE_REDRIVE_EXHAUSTED` plus the reported failure code, and the BFF now renders a `Failed` runtime status as-is instead of the desired power state, surfacing `last_error` — never a silent zombie. Behavior for VMs that never hit a terminally-failed create is unchanged. Residue idempotency of the re-executed create is pinned at the mock runtime tier and against the local stord backend (re-open with the same provisioning hints does not re-seed/resize; re-attach is idempotent); the ceph/iscsi/lvm backends carry the same idempotent open/attach contract but are not separately pinned. Design writeup: [`docs/design/issue-368-journaled-create-redrive.md`](docs/design/issue-368-journaled-create-redrive.md). (#368)
- **Storage (stord, startup log — second-pass review of #483)**: the disabled-migration startup confirmation line is restored to the daemon wiring, and now fires exactly once. #483's extraction of the startup wiring into `load_migration_materials` dropped `main`'s `else` branch that logged `storage migration is disabled: migration actions will be unavailable` for `migration.enabled = false`. The loader (`load_migration_tls` in `chv-stord-core`) still emitted its own copy of that line — it had since #252, so before #483 a disabled stord actually logged the line *twice* — but the daemon-level confirmation belonged to the wiring, and its loss was flagged in review. The line now lives in `load_migration_materials` (so it is pinned by unit tests at the wiring seam, like the rest of the wiring sequence) with the cause spelled out — `storage migration is disabled (migration.enabled = false): migration actions will be unavailable` — and the loader's duplicate emission is removed, so a disabled stord logs the line exactly once. The three enabled shapes (source-only, destination-only, both) are unchanged: they never log the disabled line, and their own startup lines (the loader's "storage migration client identity not configured" for destination-only, `main`'s "storage migration mTLS enabled" / "storage migration receiver mTLS material validated") are untouched. New unit tests in `cmd/chv-stord` pin all four shapes, including the exactly-once property.
- **BFF (volume ownership — issue #386)**: volumes created by VM import (`POST /v1/vms/import`) and VM-template instantiation (`POST /v1/vm-templates/:id/clone`) are now stamped with the creating operator (`volumes.owner_id = claims.sub`), mirroring `vm create` (`vms.rs`). Both routes are `require_operator_or_admin`, but the two INSERTs previously left `owner_id` NULL — and `require_volume_owner` rejects ownerless volumes for non-admins ("resource has no owner; admin access required") — so the operator who imported a VM or instantiated a template could not attach, snapshot, resize, or restore the volume they had just created; it was admin-only from birth. Same functional class as the clone-target ownerlessness fixed in the #381 follow-up. Ownership only tightens: no authz, role, or mTLS behavior changed — a different operator is still forbidden on the new rows, admins still bypass the owner check, and the control-plane upsert's COALESCE still never strips an owner. New integration tests (`crates/chv-webui-bff/tests/volume_creation_ownership.rs`) pin all four facts and fail against the pre-fix INSERTs. Residual: volumes created by these two paths **before** this fix remain ownerless (admin-only); see the PR for the attribution analysis and the proposed — not implemented — backfill. (#386)
- **Agent (serial console persistence — issue #476)**: the `console.log` file sink is now lossless under console-output floods. The writer task was fed from the same capacity-4096 lossy broadcast as the WebSocket live view, and its `Lagged → continue` branch silently skipped the missed messages: under CH v53.0's post-reboot serial backlog replay (byte-at-a-time delivery — 45,699 of 45,736 live messages were 1 byte in the observed run) a writer parked mid-`write_all` could fall more than 4096 messages behind the drain thread and drop bytes from the durable record while WS and scrollback stayed byte-complete (a code-path finding from the #475 live recheck, now deterministically reproduced: a flood of 4,608 one-byte fan-out messages left console.log holding only the flood's 4,096-byte tail — the head of the stream, where the kernel banner lives, was skipped). The three console sinks are now bundled in one `ConsoleFanout` type — the lossless console.log feed (an unbounded mpsc whose receiver exists before any producer can send, which also eliminates the writer's old subscribe-time loss window), the unchanged lossy live-view broadcast, and the synchronously-appended scrollback — so every producer (the serial drain loop, the abandoned-connection drain, the shutdown drain) feeds all three sinks or none; the fan-out's `send` stays await-free, preserving the #469/#471 drain-continuously reader's no-park property against the #8322 backlog-flush truncation. The WS live view deliberately keeps its skip-and-resume semantics for slow clients (recovery is reconnect + scrollback replay, and pinning per-client agent memory would be worse), but a lag is now logged with the skipped count instead of passing silently. The 10 MiB console.log wraparound cap, the 256 KiB scrollback cap, the reboot rotation, the heal gates/budget, and the boot watchdog are unchanged. (#476)
- **Storage (stord, migration mTLS observability — issue #402)**: TLS-layer migration rejections were indistinguishable sender-side and invisible receiver-side. Sender: every TLS-layer rejection — wrong CA (`UnknownIssuer`), wrong server name (`CertNotValidForName`), expired destination certificate (`Expired`) — collapsed to the single text `failed to connect to peer with mTLS: transport error`, so an operator could not tell a misconfigured CA from a wrong server name without a debugger. The sender now walks the tonic error's source chain (the technique the loopback mTLS tests already used) and surfaces the terminal rustls alert/reason in the failure message and the migration task's `error_message` (e.g. `failed to connect to peer with mTLS: transport error: invalid peer certificate: UnknownIssuer`). Receiver: a peer rejected at the TLS handshake (untrusted client CA, no client certificate) produced **no log line at all** on the destination stord — tonic completes TLS handshakes inside its hyper accept path and drops transport-level failures with at most a debug-level line carrying no peer address. The migration receiver now completes the handshake in its own accept loop before handing the connection to the tonic server, so a rejected handshake never becomes a connection and is logged at warn level with the peer address and the alert/reason — `rejected migration TLS handshake peer=127.0.0.1:54962 reason=peer sent no certificates` / `reason=invalid peer certificate: UnknownIssuer` (and, when the *sender* aborts, `reason=received fatal alert: UnknownCA`). Both changes are quality-of-failure only: everything already failed closed, and still does — the rustls `ServerConfig` is built with the same mandatory `WebPkiClientVerifier` (no `allow_unauthenticated()`, no client-auth-optional, `h2` ALPN) that tonic's `ServerTlsConfig` built internally, and the sender still refuses to run without mTLS. Surfaced text is content-free by construction: alert/reason names only, never certificate contents or key material (pinned by the new tests). (#402)
- **Release tooling (`scripts/bump-version.sh` — follow-up to the 0.3.0 release cut, PR #473)**: version bumps now escape sed BRE metacharacters before interpolating the old version into rewrite patterns. ### Fixed
- **Agent (serial console — issue #469)**: reconnecting or adopted consoles now recover the full buffered backlog instead of truncating it. The console broadcaster's per-connection read loop read through `tokio::fs` (one blocking-pool dispatch plus a runtime wakeup per read) and awaited the scrollback `RwLock` between reads; both gap classes could let Cloud Hypervisor v53.0's serial flush session hit `EAGAIN` and silently stop delivering (upstream #8322: one-byte non-blocking writes with no EPOLLOUT retry — a 20 ms-polling reader measured a 278-byte hard stop and a ~0.6–1.3 KB/s crawl against a ~74 KB backlog). The reattach reader is now a dedicated blocking-pool thread issuing plain blocking `read()`s back-to-back with no awaits between reads, keeping the socket empty through a flush session by construction — the 96 KiB one-byte-at-a-time stand-in transfers with zero session breaks, and the pinning test fails when a 20 ms inter-read sleep is injected. The boot watchdog's stall window is progress-based (any console growth resets it), so a crawling-but-alive console is waited out however far past a full-rate boot's timeline the crawl stretches, while a genuinely dead stream still times out; both semantics are pinned by tests. The reboot rotation, the heal gates and budget, the 256 KiB scrollback cap, and the WS scrollback contract are unchanged. (#469)
- **Agent (adopted VMs — issue #409)**: a VM adopted after an agent restart could sit wedged half-booted forever while `vm.info` reported `Running`. Bounded to one remediation reboot per VMM generation per agent process, so a stale detection can never become a reboot storm. VMs with a live serial-manager thread, an unreadable `/proc` (e.g. hidepid), tracked (`Owned`) VMs, Pty-transport VMs, and deliberately `Paused` VMs are never selected. (#409)
- **Agent (delete after restart — issue #405)**: deleting a VM that was created before an agent restart leaked its stord volume attachments and nwd tap devices — the side-effect map lived in process memory, so the delete drained nothing while reporting success (observed live in the M4.7 fault matrix: two pre-restart deletes left orphaned taps that only the deploy teardown removed, while post-restart deletes detached cleanly). - **BFF (idempotency — issue #406)**: a retried `vm delete` of a retained VM returned `HTTP 500 INTERNAL_ERROR` instead of a clean idempotent success. The BFF derives per-resource idempotency keys (`delete-vm-<vm_id>`, `resize-vm-<vm_id>-<cpu>-<mem>`) and recorded them as plain UNIQUE INSERTs into the shared `operations` table; with the M2.5 authority-side retention keeping the VM rows after a delete, the retry re-entered the handler with the same key and the UNIQUE violation surfaced as an unhandled 500 (found live by the M4.7 fault-matrix run 1, F7). A new shared helper (`handlers/operations`) now checks for a recorded operation *before* any mutation — inside the handler's existing `BEGIN IMMEDIATE` transaction, mirroring the controlplane store's `ON CONFLICT (idempotency_key) DO NOTHING` + re-select — and a collision replays the recorded original outcome (200 with the recorded `task_id` and its current `recorded_status`) without re-executing the mutation. The delete key stays per-VM (one delete is the intent); the resize key is args-hashed so a genuinely *different* resize is a fresh operation (a per-VM key would silently replay the first outcome and swallow the new intent) while a same-args retry still replays. - **Storage (stord, data integrity — issue #392)**: migration finalize now verifies the destination's *data*, not just the protocol. Previously the receiver replied `FinalizeAck{verified:true}` unconditionally and the sender sent an empty `volume_checksum`, so the only integrity mechanism was the per-chunk CRC32 — a corrupted, truncated, or externally modified destination volume still finalized as `Completed`. At finalize the sender now streams a full-volume SHA-256 digest over the source (via the same `read_block` path as bulk copy, never holding the volume in memory) and carries it in `FinalizeComplete.volume_checksum` in a versioned, self-describing format (`"sha256:"` + 32 raw bytes, documented in the proto); the receiver re-computes the same digest over the destination after its final flush and sets `verified` accordingly. Fail-closed on every leg: digest mismatch ⇒ `verified=false` with a precise, content-free error ("destination digest mismatch: expected sha256:…, got sha256:…" — never volume data); unknown/unsupported digest format ⇒ `verified=false` naming the format (forward-compatible detection, no silent misinterpretation); unreadable destination ⇒ `verified=false`; and the sender treats `verified=false` as a migration failure — task → `Failed` with `Status::data_loss` (same integrity class as a chunk CRC mismatch), so `Completed` genuinely means "destination verified". Per-chunk CRC32, ack semantics, and the protocol are otherwise unchanged. Cost: one additional sequential full-volume read on each side at finalize. Four data-path fixes: (1) **round-ack deadlock** — the receiver only logged `RoundComplete` and sent nothing, so the sender blocked forever waiting for a round acknowledgment after the first dirty sync round; the receiver now always answers `RoundComplete` with an `Ack` carrying its highest processed sequence number, which both acknowledges the round and flushes its ack window. (2) **ack-window flush mismatch** — the receiver acknowledged only every 64 chunks with no final flush, so any phase whose chunk count was not a multiple of 64 (at 4 MiB blocks: any volume under 256 MiB) timed out after 30 s; the receiver now flushes outstanding acks at `FinalSync` and before `FinalizeAck`, the sender drains after `RoundComplete`/`FinalSync` instead of at a point the receiver can never observe (end of bulk copy), and the FinalizeAck wait tolerates in-flight boundary acks. (3) **Init handshake deadlock** — the sender awaited the stream response before sending `InitMigration`, but the tonic server handler blocks reading the first message before responding, so the stream could never start; the sender now queues `InitMigration` before opening the stream. (4) **gRPC message-size limit** — a 4 MiB `BlockChunk` plus protobuf overhead exceeds tonic's default 4 MiB decode limit, so the receiver rejected every real chunk with `OutOfRange`; both serving paths (mTLS TCP listener and Unix socket) now accept migration messages up to 8 MiB.
