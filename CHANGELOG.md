### Added
- **Firewall boundary (network policy baseline + dispatch fencing — issue #355, PR 3 of the adopted decomposition, DP4 + DP5 + DP7)**: the ruled DP4 semantics land — `[]` (and a never-set ruleset) stop meaning "no policy" and start meaning "no *user* rules": the boundary is **baseline + default-deny**, never a bare default-deny (the #360 cutoff, which would cut a rule-less network's guests off entirely, including DHCP) and never an unfiltered skip (the pre-DP4 behavior). **The baseline** (`chv_common::firewall::baseline_policy_json()`): DHCP (UDP 67/68, both directions — belt-and-suspenders alongside conntrack, which tracks the initial `0.0.0.0:68 → 255.255.255.255:67` broadcast least reliably) and DNS (UDP/TCP 53 inbound; replies ride the engine's established/related head rule); everything else inside the CHV traffic boundary stays default-deny. Vocabulary disclosure: the rule language has no destination CIDR and the nwd engine is unchanged (§7), so the allows are port-scoped on CHV-owned interfaces — a guest may also reach a non-gateway DNS resolver on port 53. **Resolved at three producer sites**: the orchestrator's dispatch arm (empty/never-set rulesets dispatch the baseline instead of no-op'ing — replaces the #360 filter), the agent's carrier handler (belt-and-suspenders for direct RPC callers), and the Core executor's attach path (never-set, blank, and `[]` snapshots all apply the baseline before the NIC attaches — rule-less networks get a filtered boundary at materialization, the issue's (a) half). The orchestrator's VM-spec assembly stopped filtering empty rulesets: `[]` rides the spec as-is and the attach path resolves it. **DP5 (clear semantics)**: the BFF's clear summary now names the truth — "cleared to the baseline (DHCP/DNS/conntrack allowed, default-deny otherwise)" — a cleared network is a live, filtered network, not a teardown and not the pre-baseline stale-policy residual. **DP7 (dispatch fencing)**: the agent keeps a per-network last-APPLIED generation fence (`AgentServer::network_policy_fence`, in-memory) — a dispatch whose `meta.desired_state_version` parses BELOW the recorded generation is an idempotent no-op Ack, so an out-of-order fan-out result or an older operation's retry can never regress a newer policy; the generation is compared NUMERICALLY (never string-wise — "9" sorts above "10" lexicographically), a non-numeric version fails closed with `invalid_argument`, and the fence advances ONLY on a successful nwd apply (a refused generation never blocks an older one that still matches the last applied state) and MONOTONICALLY (strictly-bigger only, under the lock — concurrent dispatches to the same network both reading the old mark cannot regress the high-water mark). The attach path needs no fence by construction (the spec assembly reads the current NDS ruleset at dispatch time). **Unchanged, disclosed**: the legacy `apply_network_desired_state` and reconcile paths keep the #360 skip (design §6); the attach path still calls the unchecked nwd variant, so a semantic refusal there is swallowed (the follow-up flagged in PR 1 — a refused baseline leaves the network exactly as unfiltered as the pre-DP4 skip did); a missing/tombstoned NDS row on dispatch remains a no-op Succeeded. **End-to-end contract row, proven as a byte-identity chain across the mock tiers**: BFF tests pin payload → NDS bytes + journaled generation; orchestrator tests pin NDS bytes → RPC `policy_json` verbatim (baseline for `[]`) + generation riding the request + the op reaching Succeeded; agent tests pin RPC bytes → nwd `set_firewall_policy_checked` bytes verbatim with the fence no-op'ing stale generations; runtime-ch tests pin the attach-time baseline application before the NIC attaches. The real-host leg (nft chains changed on a live node) is the M4.4 successor qualification run's Leg B, whose task-surface detection and tick-paced warn already landed. Tests: the baseline's engine-vocabulary pin (the M4.4 N7 class, in chv-common); the attach-time baseline pin (4 no-user-rules snapshot shapes, one application each, constant content-derived version); the carrier's DP4 pin (empty ruleset → the shared baseline verbatim at nwd); three DP7 pins (stale generations no-op — including the numeric-vs-lexicographic discriminator "9" after "10"; a failed apply does not advance the fence; non-numeric generations fail closed); the orchestrator's empty-ruleset arm pin (baseline dispatched verbatim with the generation riding the request, op Succeeded); and the BFF clear-summary pin (DP5). Refs #355.
- **BFF (network policy journaling route — issue #355, PR 2 of the adopted decomposition, DP1 + DP6)**: `POST /v1/networks/update` — the first producer of the PR 1 `UpdateNetworkPolicy` dispatch carrier (#565), closing the route's original lie: a `firewall_rules` update was persisted to `network_desired_state` and answered HTTP 200 with a prose `policy_application` note while **nothing ever dispatched it to a node**. **Journaling (DP1, the CreateVolume precedent)**: when the request carries `firewall_rules`, the route journals an `Accepted` `UpdateNetworkPolicy` operation **in the same transaction** as the desired-state write — idempotency key `update-network-policy-{network_id}-{generation}` (per-generation, so every mutation mints its own task; a retried identical payload journals a fresh op that re-applies the same rules — idempotent in effect, disclosed), `resource_kind 'network'`, owner stamped (`requested_by`, the #386 discipline), the bumped `desired_generation` riding the row (the UPDATE now `RETURNING`s it — the DP7 fence's carrier, enforced by the PR 3 entry above). The PR 1 orchestrator arm claims the row and fans the stored ruleset out to every node with a live attached VM on the network. **Deliberately journaled only when the firewall field rode the request** — other NDS-field updates (cidr, DHCP, ...) bump the generation but mint no operations (they dispatch nothing), and a name-only update touches neither; an empty ruleset (`[]`) journals too (a real mutation — the dispatch leg carries the DP4 baseline, per the PR 3 entry above). **Reporting (DP6)**: the `policy_application` prose notes are **replaced** by the standard task surface — a firewall-carrying update answers with the mutation shape (`{accepted, task_id, network_id, summary, next_refresh_path}`), the summary honest about the dispatch semantics (for `[]`, naming the DP5 clear semantics — the baseline, per the PR 3 entry above); terminal failures surface their cause through the #502 task reads, and the network detail's `last_task` now resolves to `UpdateNetworkPolicy` (the detail query already keys on `resource_kind 'network'` — zero extra work, pinned). **Response-shape disclosure**: the shape is keyed on the request — non-firewall updates keep the read-after-write detail response they always returned (they journal nothing); the task shape carries `network_id` top-level and the detail shape carries it nested under `detail`, and the UI's `updateNetwork` (declared return type `{network_id: string}`, response discarded beyond cache refresh) never reads either — no consumer changes (chvctl has no `network update` verb; the contract harness has no row for the route). Also folded from review: the update transaction now opens `BEGIN IMMEDIATE` (the network_delete/operations precedent) so two concurrent updates cannot both read generation N and mint the same per-generation idempotency key, the legacy-residue case (an existing, non-tombstoned network with no `network_desired_state` row — silently no-opped by the pre-#355 UPDATE — now fails loud with a clear error instead of minting a generation-less operation), and the op-INSERT failure path routes through the #406 `map_operation_insert_error` 409 discipline (the DeleteVm/ResizeVm idiom: a key collision fails closed with a Conflict naming the recorded operation, never an opaque 500 — unreachable defense-in-depth under the serialized writer). The route's auth/ownership/tombstone gates are unchanged (operator-or-admin, `require_network_owner`, the #499 DP9 predicate). Tests (`network_policy_reporting.rs`, migrated + extended): the task-shape response with the journaled row pinned field-by-field (type, Accepted, per-generation key, owner, generation), the detail's `last_task` resolution, the clear story (apply + clear mint two per-generation tasks, the honest clear summary), the non-firewall no-journaling pin (name-only and cidr-only: detail shape, zero operations, generation still bumps), the unchanged vocabulary/rejection pins, and a concurrency pin (the quota-race suite's temp-file WAL pool shape: 8 simultaneous firewall updates → 8 distinct per-generation tasks, consecutive keys, no lock-contention failures, generation advanced exactly 8 times). Refs #355 (closed by the PR 3 entry above).
- **Agent / control plane (network firewall-policy dispatch carrier — issue #355, PR 1 of the adopted decomposition, Option A + B baseline)**: the network-policy surface's dispatch carrier, landed dead-but-live with **no producer and zero behavior change** — no route journals an `UpdateNetworkPolicy` operation until the BFF leg lands (PR 2; the #513/#522 PR 1 precedent). The finding it serves: `POST /v1/networks/update` with `firewall_rules` persists to `network_desired_state` and is **never dispatched to any node** (dead configuration with a 200), and rule updates after a topology exists never propagate (only a brand-new VM create carries the new snapshot, via the already-shipped attach-time policy join). Four additive pieces: (1) **proto** — an `ApplyNetworkPolicy` RPC on the node `LifecycleService` beside `CreateVolume`/`DeleteVolume`, request `{meta, node_id, network_id, policy_json}` (the stored `firewall_rules_json` verbatim; the NDS generation rides `meta.desired_state_version` — the DP7 fence, enforced from PR 3); (2) **node_client** — the CP-side `apply_network_policy` dispatch method with the house transport discipline (timeout, circuit breaker, operation-id metadata); (3) **orchestrator** — the `"UpdateNetworkPolicy"` dispatch arm, intercepting before single-node resolution exactly like `UpdateOverlay` (DP2: networks are fleet-wide — `networks.node_id` is NULL for the operator-created networks that carry rules — and materialization is per-node and lazy), resolving the target set as **nodes with ≥1 live attached VM on the network** (`vm_nic_desired_state` × `vm_desired_state`, tombstone-aware: a `Deleting` VM's node is excluded), fanning out with the UpdateOverlay discipline (#378 §7 all-refusals fast-fail terminal `Failed`/`UNSUPPORTED_BY_AGENT` without retry, mixed failures on the shared retry curve, #502 partial-success roll-up naming both sets); zero targets is a no-op `Succeeded` (a fleet network with rules but no attached VMs is the normal create-then-populate order — the attach-time snapshot applies the policy at first materialization), and a missing or `'Deleting'` NDS row is likewise a no-op `Succeeded` (a policy update racing a network delete has nothing to apply); (4) **agent** — the `apply_network_policy` handler: safe-id rejection at the node boundary (the network id becomes the nft table name), fail-closed parse of `policy_json` BEFORE nwd (the M4.4 N7 class — the CP is a trusted-but-buggy peer), application through a new **checked** `NwdClient::set_firewall_policy_checked` — the same nwd `SetFirewallPolicy` call the attach-time path makes, but inspecting the inner result — and the **#360 discipline unchanged by this PR**: a semantically empty ruleset is a no-op ack, never dispatched (nwd engages default-deny even for `[]`, which would cut the network's guests off entirely, including DHCP); PR 3 flips that at the policy boundary per the ruled DP4 (`[]` = no user rules → baseline DHCP/DNS/conntrack allows + default-deny). **The review-discovered swallow, fixed in-carrier and disclosed**: nwd reports SEMANTIC refusals (unknown topology `NotFound`, engine failure, vocabulary rejection) as a gRPC `Ok` wrapping an `err_result`, and the pre-existing shared `NwdClient::set_firewall_policy` maps only the transport error — so a caller using it acks a false success when the apply was refused (the #355 lie in task form). The carrier therefore uses the checked variant (the `ensure_network_topology` discipline); the unchecked method stays byte-identical for its other caller — the attach-time path, whose swallow of nwd refusals is a **pre-existing gap this PR does not change (zero-behavior-change contract), flagged for follow-up**. **The M2.2b carve-out, the one load-bearing difference from every sibling nwd-side-effect RPC: the handler is deliberately ACCEPTED in core-managed mode** — policy application already runs behind the Core authority at VM attach (the core executor's `set_firewall_policy` call), the Core store models no network state to journal into, and the CP operations row is the journal; what M2.2b refuses is the legacy fragment path's NodeCache network-axis writes and unprompted topology ensure, and this handler does neither (it applies policy to an EXISTING topology — nwd fails closed on an unknown one — and writes no cache). The CP-side gRPC lifecycle shim answers `unimplemented` naming the adopted BFF-direct journaling decision (the #513/#522 convention). Tests: agent-tier (6) pin the non-empty apply byte-identically through a recording mock nwd, the **nwd-refusal surfacing** (an `err_result` fails the operation with the code and summary riding the error — the mock proves the call reached nwd, so it cannot pass vacuously), the empty-ruleset no-op (summary-pinned so it cannot pass vacuously), the unsafe-id and malformed-JSON boundary refusals, and the **core-managed acceptance pin** (a core authority attached, the carrier still applies — the test names the carve-out, so a future copy-paste of the sibling `unimplemented` guard fails loudly); CP-tier (7) pin the fan-out to live-attached-VM nodes only (a `Deleting` VM's node excluded), the NDS-generation threading, the empty-ruleset and zero-target no-op successes, the missing/Deleting-NDS no-op successes (with a live target on the tombstoned network proving the branch is not vacuously safe), the **mixed-failure retry semantics** (one node reachable, one node's transport down → `RetryPending`, not terminal — the overlay arm's discipline pinned for the network-policy leg), the **partial-success all-refusals shape** (one node acks, one refuses → terminal `Failed`/`UNSUPPORTED_BY_AGENT` with the applied set named beside the refusing set), and the all-refusals terminal fast-fail with no re-dispatch across ticks. **Living-doc note**: the M2.2b single-writer enumeration in `docs/specs/cellhv-core-journal-executor.md` — which states every legacy nwd-side-effect handler fails closed in core-managed mode — gains a dated 2026-10-08 note naming this carrier as the one ruled exception (the design doc §3 DP3), so the spec does not lie by omission. Design writeup (adoption record, 2026-10-08: Option A + B baseline, DP4 ruled baseline+default-deny, DP1-DP3/DP5-DP7 as recommended, Option C rejected; this is PR 1 of 3): [`docs/design/issue-355-network-policy-dispatch.md`](docs/design/issue-355-network-policy-dispatch.md). Previously `migration.enabled = true` made the *client* identity mandatory (`client_cert_path`, `client_key_path`, `ca_cert_path`, `dest_server_name` all required), so a stord that should only ever *receive* migrations could not be configured without minting and maintaining a client identity it would never use (found in the M4.6 qualification, which carried an unused client identity as a workaround). The two migration halves are now independently optional under `enabled = true`: omitting all four client fields configures a destination-only stord whose outbound migration actions fail with the sender's existing `failed_precondition` error (unchanged no-plaintext-fallback behavior); omitting all receiver fields keeps the existing source-only stord. Each half remains all-or-nothing within itself (a partial half is still a startup error), `enabled = false` with any field anywhere in the section is still a startup error (#393/#395 semantics), and `enabled = true` with *neither* half configured is a new startup error — an enabled migration section that configures nothing is a misconfiguration, previously masked by the client-fields requirement. Behavior change boundary: the only configs whose outcome changes are ones that are startup errors today (destination-only) and now start; nothing that starts today stops starting — source-only, both-halves, disabled-clean, and all error cases (partial halves, `enabled = false` contradictions, unreadable/invalid/mismatched material) are byte-for-byte the same validation paths. Operators wanting a destination-only stord: set `enabled = true` plus the four receiver fields and drop the client identity entirely (example in `docs/examples/stord.toml`).

The fix adds exactly one admissible shape beside JSON: a non-GET request with `Content-Type: multipart/form-data` **and a non-empty `x-csrf-token` header** passes the gate; multipart without the header is 403 `CSRF_REJECTED` before routing; every other content type (the form-native `application/x-www-form-urlencoded` and `text/plain`, and a missing one) keeps the exact pre-#496 415. **The enforcement shape, disclosed precisely**: the marker lives in the middleware (one enforcement point, no route exemptions, the body is never read — the multipart stream is left intact for the handler), and it is header-*presence*, not a cryptographically verified token — because the tree has no CSRF token issuance/verification to verify against (the `x-csrf-token` name existed only in the CORS allow-list; introducing a real token model is a broader redesign, explicitly non-scope). - **Agent (serial console — issue #469)**: reconnecting or adopted consoles now recover the full buffered backlog instead of truncating it. The console broadcaster's per-connection read loop read through `tokio::fs` (one blocking-pool dispatch plus a runtime wakeup per read) and awaited the scrollback `RwLock` between reads; both gap classes could let Cloud Hypervisor v53.0's serial flush session hit `EAGAIN` and silently stop delivering (upstream #8322: one-byte non-blocking writes with no EPOLLOUT retry — a 20 ms-polling reader measured a 278-byte hard stop and a ~0.6–1.3 KB/s crawl against a ~74 KB backlog). The reattach reader is now a dedicated blocking-pool thread issuing plain blocking `read()`s back-to-back with no awaits between reads, keeping the socket empty through a flush session by construction — the 96 KiB one-byte-at-a-time stand-in transfers with zero session breaks, and the pinning test fails when a 20 ms inter-read sleep is injected. The boot watchdog's stall window is progress-based (any console growth resets it), so a crawling-but-alive console is waited out however far past a full-rate boot's timeline the crawl stretches, while a genuinely dead stream still times out; both semantics are pinned by tests. At finalize the sender now streams a full-volume SHA-256 digest over the source (via the same `read_block` path as bulk copy, never holding the volume in memory) and carries it in `FinalizeComplete.volume_checksum` in a versioned, self-describing format (`"sha256:"` + 32 raw bytes, documented in the proto); the receiver re-computes the same digest over the destination after its final flush and sets `verified` accordingly.
