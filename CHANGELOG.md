## [Unreleased]

### Added
- **Control plane (credential encryption key-source observability — issue #336)**: startup logging now says which secret the S3 credential cipher was keyed from. A dedicated `CHV_ENCRYPTION_KEY` logs an info line; the legacy `CHV_JWT_SECRET` fallback — reached only by pre-#335 hosts and env-driven deployments without `/etc/chv/encryption.env`, since both install surfaces (`install.sh` and the package postinst) mint a dedicated key — now logs a startup **warning** stating plainly that S3 credentials are being encrypted under the JWT signing secret, that rotating `CHV_JWT_SECRET` will invalidate all stored S3 credentials (fail-closed `AuthFailed`, re-entry required), and pointing at the DR runbook for migrating to a dedicated key. Previously the fallback was completely silent at startup, and a routine JWT-secret rotation surfaced later as opaque S3 auth failures. The DR runbook (`docs/runbooks/control-plane-dr.md`) now documents how to restore or mint the dedicated key on a replacement host, and the fallback's rotation hazard with a zero-re-entry migration (copy the current `CHV_JWT_SECRET` value into `/etc/chv/encryption.env`, then rotate the JWT secret freely). Encryption behavior is unchanged — same key derivation, same ciphertexts, same fallback semantics, no new config knobs; only log lines and documentation are new. Whether to drop the fallback entirely remains a maintainer decision tracked in #336.

### Fixed
- **Release tooling (`scripts/bump-version.sh` — follow-up to the 0.3.0 release cut, PR #473)**: version bumps now escape sed BRE metacharacters before interpolating the old version into rewrite patterns. The script built its sed commands as `s/${OLD_VERSION}/${NEW_VERSION}/g`, so with `OLD_VERSION=0.2.0` the pattern was the regex `0.2.0` — whose dots match any character — and it matched `0.200` inside the bridge CIDR `10.200.0.1/24`, corrupting six lines across `docs/DEPLOYMENT.md` and `scripts/install.sh` during the 0.3.0 cut, including the installer's runtime `INSTALL_CHV_BRIDGE_CIDR` default (`10.200.0.1/24` → `10.3.0.0.1/24`; PR #473 repaired all six by hand and flagged the script as this follow-up). Every sed call site that interpolates a version now matches it literally via an `escape_sed_pattern` helper: the five global replaces (README, DEPLOYMENT, install.sh, hosting files), the anchored Cargo.toml rewrite, the UI `package.json`/`package-lock.json` sed fallback, and the sidebar label — while the other release scripts (`version.sh`, `build-packages.sh`, `build-release.sh`, `scripts/release/*`) were audited and interpolate no version into any sed regex. Replacement behavior is otherwise unchanged: `v0.2.0`, `chv-v0.2.0-alpha`, `Version: 0.2.0`, and `version = "0.2.0"` references all still bump, with no word-boundary anchoring added. A new self-contained regression smoke test (`scripts/smoke-bump-version.sh`, wired into CI beside `smoke-version.sh`) runs the real script against a fixture containing genuine version refs plus CIDR trap lines and asserts the refs bump while the traps stay byte-identical — it fails against the pre-fix script with the exact observed corruption. Known residual, unchanged by design: a CIDR or other string that *literally contains* the version substring (e.g. a future bridge CIDR `10.3.0.1/24` at version `0.3.0`) is still rewritten by the intentional global replace; preventing that would require context-aware matching that breaks the embedded-ref contract. (#474)

Security: closes the **CVE-2026-27211** / GHSA-jmr4-g2hv-mjj6 exposure (High; host-file exfiltration via QCOW backing-file abuse; affected v34.0–v50.0) **with runtime proof** — the full chain was reproduced at v43 under the CHV invocation shape and fails closed at v53 on every entry point — and closes **CVE-2026-45782** / GHSA-f47p-p25q-83rh (High; use-after-free in virtio-block async I/O, guest-triggerable with default async block I/O; affected v21.0–v51.1) at the records tier; no newer advisory affects v53.0. Functional gains at v53.0: disk-image locking; the M4.3 #345 stop wedge is gone (clean v43-control A/B); the upstream v50.0 serial fixes (pty flush gate, socket fd leak) and v53.0 pre-connect buffering are in. Known cost — the v53.0 serial defects: the silent serial-manager thread death survives the upgrade (contained by the agent's mitigation layers: the reboot force-rotation, the #409 heal detector, and the #469 drain-continuously reader below), and upstream #8322's flush-session delivery stalls for any reader with inter-read gaps (contained by the same drain-continuously reader); the serial-console gate above KVM-VERIFIED survives unchanged. Existing hosts keep v43.0 until they reinstall or reprovision (the already-installed branch of the installer is unchanged; upgrade semantics remain ADR-007/D8 territory) — such hosts remain in the CVE-affected range. ([#468](https://github.com/kubedoio/chv/pull/468))
- **Storage (stord, behavior change — issue #395)**: the migration *client* TLS config is now gated on `migration.enabled` exactly like the receiver half: setting any client field (`client_cert_path`, `client_key_path`, `ca_cert_path`, `dest_server_name`) while `migration.enabled = false` is a **startup error** instead of a silently ignored half-configuration. ### Fixed
- **Agent (serial console — issue #469)**: reconnecting or adopted consoles now recover the full buffered backlog instead of truncating it. The console broadcaster's per-connection read loop read through `tokio::fs` (one blocking-pool dispatch plus a runtime wakeup per read) and awaited the scrollback `RwLock` between reads; both gap classes could let Cloud Hypervisor v53.0's serial flush session hit `EAGAIN` and silently stop delivering (upstream #8322: one-byte non-blocking writes with no EPOLLOUT retry — a 20 ms-polling reader measured a 278-byte hard stop and a ~0.6–1.3 KB/s crawl against a ~74 KB backlog). The reattach reader is now a dedicated blocking-pool thread issuing plain blocking `read()`s back-to-back with no awaits between reads, keeping the socket empty through a flush session by construction — the 96 KiB one-byte-at-a-time stand-in transfers with zero session breaks, and the pinning test fails when a 20 ms inter-read sleep is injected. The boot watchdog's stall window is progress-based (any console growth resets it), so a crawling-but-alive console is waited out however far past a full-rate boot's timeline the crawl stretches, while a genuinely dead stream still times out; both semantics are pinned by tests. The reboot rotation, the heal gates and budget, the 256 KiB scrollback cap, and the WS scrollback contract are unchanged. (#469)
- **Agent (adopted VMs — issue #409)**: a VM adopted after an agent restart could sit wedged half-booted forever while `vm.info` reported `Running`. If the previous agent's serial connection was reset with unread console data in flight (e.g. the agent was SIGKILLed mid-boot), Cloud Hypervisor's serial-manager thread dies silently on `ECONNRESET` — the listener stays bound but is never accepted again, the guest's serial TX fills, PID 1 blocks in its console writes, and logind never starts. `start_vm`'s already-running branch — the first reconciliation point after adoption — now detects the proven absence of the `serial-manager` thread via a `/proc` scan and heals with the live-proven `vm.reboot` remediation, which re-creates the VM in the same VMM process with a fresh serial manager and re-binds the listener; the existing rotation then moves the parked broadcaster onto the new connection and capture resumes. Bounded to one remediation reboot per VMM generation per agent process, so a stale detection can never become a reboot storm. VMs with a live serial-manager thread, an unreadable `/proc` (e.g. hidepid), tracked (`Owned`) VMs, Pty-transport VMs, and deliberately `Paused` VMs are never selected. (#409)
- **Agent (delete after restart — issue #405)**: deleting a VM that was created before an agent restart leaked its stord volume attachments and nwd tap devices — the side-effect map lived in process memory, so the delete drained nothing while reporting success (observed live in the M4.7 fault matrix: two pre-restart deletes left orphaned taps that only the deploy teardown removed, while post-restart deletes detached cleanly). The delete drain now falls back to a durable observed-attachment source — the NodeCache that the startup rebuild re-seeds from the Core store — issuing stord `DetachVolumeFromVm` (plus `CloseVolume` where a handle was durably recorded) and nwd `DetachVmNic` inside the already-fenced delete. The fallback is idempotent and fail-open exactly like the in-memory drain (a failed cleanup step cannot fail the delete); the tracked path is byte-identical and pinned never to consult the fallback. Known residuals: a post-restart delete still cannot close handle-less stord sessions (the M2.2a durable-handle debt, narrowed but not eliminated), and network topology teardown stays with network delete / node reprovision. (#405)
- **Agent (delete/force-stop honesty — issue #351)**: `vm delete`'s force path and both of `vm stop`'s force branches removed the runtime-map entry, unlinked the api socket / pid file / persisted config, and reported success even when the SIGKILL was **refused** (an adopted pid whose identity can no longer be proven, e.g. the VMM binary was replaced on disk while the process ran) or **ineffective** (a D-state process survives SIGKILL) — leaving a live VMM holding the runtime dir, sockets, and disk while the deleted VM's state no longer referenced it (the #345 bug class). All three sites now share the #348 kill-then-confirm-death helper; on a refused or ineffective kill over a live VMM the runtime-map entry is restored (truthful state: a retry re-validates liveness, a later start refuses to double-spawn) and the operation fails loudly with the documented operator escape (SIGKILL the pid directly, then retry). Already-dead cases — a `Dead` handle, a reaped child, an adopted pid that has left `/proc` — still delete successfully; only a surviving VMM fails. (#351)
- **Agent (legacy firewall policy — issue #360)**: both legacy-mode call sites that dispatch firewall policy to nwd (`apply_network_desired_state` and the `reconcile_networks` loop) could forward a semantically empty ruleset — and nwd's engine engages default-deny even for an empty ruleset, cutting the network's guests off entirely, including DHCP. An empty ruleset is now skipped with a warning, reusing the exact predicate the core-managed path already filters with; non-empty dispatch is byte-identical (same RPC, same serialized policy bytes). Core-managed mode was already guarded and is unchanged. (#360)
- **UI/BFF (dead firewall surface — issue #355, phase 1)**: the firewall-rules editor and its `/v1/firewall-rules` CRUD were dead end-to-end — the backing `firewall_rules` table was read by nothing on the dispatch path, and the editor's field dialect (`ingress`/`egress`, `allow`/`deny`, `port_range`, …) was rejected by the engine-vocabulary validation on the real path, so the surface could only ever fail or mislead. Removed across the UI and BFF; the dead table is dropped by forward-only migration `0056` (its rows were never read, so no live configuration is lost). The qualified attach-time path (`networks/update` → `network_desired_state.firewall_rules_json` → orchestrator dispatch) is unchanged; live re-dispatch of policy updates to already-attached VMs remains open under #355. (#355)
- **Install (from-GitHub path — issue #440)**: the from-GitHub install path could not complete regardless of repository — `releases/latest` returns 404 until a stable release exists (the endpoint ignores prereleases such as `nightly`), and the fallback then constructed a `releases/download/v0.2.0/…` tarball URL that no release ever carried. The release pipeline now attaches `chv-<version>-linux-amd64.tar.gz` plus a `.sha256` checksum at the exact URL the installer constructs, through a shared tarball assembler (`scripts/release/assemble-tarball.sh`) extracted from `build-release.sh` — which also fixes workflow drift that would have shipped a tarball the installer immediately rejects (a missing `tmpfiles/chv-node.conf` the installer fails closed without, no tarball checksum, and `|| true`-guarded copies that could drop inputs silently). The installer itself now fails fast with an explanation and the documented alternatives when no stable release exists, and on a download failure probes whether a Release exists for the tag before printing the same alternatives, instead of cascading into a cryptic curl error. Success-path URL construction is unchanged; the download path activates with this release's tag. (#440)
- **Install/config correctness (issues #424, #425, #426, #430, #431)**: five small fixes — the reference `packaging/config/chv.yaml` now declares `authority_mode: core-managed` like every shipped config (the file is reference-only, but it was wrong); `install.sh`'s `GITHUB_REPO` default points at the real `kubedoio/chv` repository (the previous `cellhv/chv` default 404s — releases exist only on `kubedoio/chv`); `docs/examples/agent.toml` binary paths match the installed `/usr/bin` locations; the load-test script's default URL points at the BFF on `127.0.0.1:8080` (the previous default, port 8444, is the agent serial console); and `kvm-smoke.sh` selects the per-arch Cloud Hypervisor static asset (x86_64 unsuffixed, aarch64 `-aarch64`). (#424, #425, #426, #430, #431)
- **chvctl (dead surface — issue #427)**: `chvctl upgrade` (start/status/rollback/list) targeted `/v1/upgrades` routes that were never registered in the BFF — the command could only ever fail at runtime with a 404 (its backing orchestration stack was deleted as dead code in #213). The subcommand is removed from the CLI and from `chvctl --help`; the manual upgrade procedure remains documented in `docs/OPERATIONS.md`. (#427)
- **Packaging (RPM version ordering — issue #432)**: `scripts/version.sh` emitted RPM pre-release suffixes with `^` — RPM's *post-release* operator, which sorts above stable — and a dash-munged override form with the same trap, so a nightly or RC RPM could sort above the stable release. All RPM outputs now use the `~` pre-release operator, identical to the Debian output (`--rpm`/`--deb` are pure aliases), so `nightly < RC < stable` holds on both formats through one mechanism, proven on the real RPM version comparator. Stable-channel output is byte-identical. (#432)
- **UI (design tokens — issue #429)**: UI components consumed CSS custom properties that were never defined in `ui/src/app.css` — transitions silently not applying, status colors falling back to inherited values in light mode. The full gap set is now defined: the motion tokens (`--duration-fast`, `--duration-normal`, `--ease-default`, per DESIGN.md's Motion spec), `--shadow-glow-success`, `--radius-full`, the fifteen light-scope `--status-{healthy,warning,degraded,failed,unknown}-{bg,border,text}` tokens (following the dark block's derivation pattern), and the `--color-ink/-muted/-line/-border` aliases mapped to themed variables so both themes stay correct. (#429)
- **BFF (idempotency — issue #406)**: a retried `vm delete` of a retained VM returned `HTTP 500 INTERNAL_ERROR` instead of a clean idempotent success. The BFF derives per-resource idempotency keys (`delete-vm-<vm_id>`, `resize-vm-<vm_id>-<cpu>-<mem>`) and recorded them as plain UNIQUE INSERTs into the shared `operations` table; with the M2.5 authority-side retention keeping the VM rows after a delete, the retry re-entered the handler with the same key and the UNIQUE violation surfaced as an unhandled 500 (found live by the M4.7 fault-matrix run 1, F7). A new shared helper (`handlers/operations`) now checks for a recorded operation *before* any mutation — inside the handler's existing `BEGIN IMMEDIATE` transaction, mirroring the controlplane store's `ON CONFLICT (idempotency_key) DO NOTHING` + re-select — and a collision replays the recorded original outcome (200 with the recorded `task_id` and its current `recorded_status`) without re-executing the mutation. The delete key stays per-VM (one delete is the intent); the resize key is args-hashed so a genuinely *different* resize is a fresh operation (a per-VM key would silently replay the first outcome and swallow the new intent) while a same-args retry still replays. Covers `vm delete` and `vm resize` (the two retry-reachable surfaces with client-supplied VM ids); `vm start/stop/reboot` go through the controlplane's already-idempotent path, and `create`/`clone`/`import` embed server-generated VM ids so their keys cannot collide. First-operation semantics and retention behavior are unchanged; a genuinely unrecoverable insert failure fails closed with a 409 naming the idempotent-retry condition instead of a 500 (classified by a re-select heuristic, not sqlx error inspection — unreachable defense-in-depth under `BEGIN IMMEDIATE` + the in-tx pre-check). (#406)
- **Storage (stord, data integrity — issue #392)**: migration finalize now verifies the destination's *data*, not just the protocol. Previously the receiver replied `FinalizeAck{verified:true}` unconditionally and the sender sent an empty `volume_checksum`, so the only integrity mechanism was the per-chunk CRC32 — a corrupted, truncated, or externally modified destination volume still finalized as `Completed`. At finalize the sender now streams a full-volume SHA-256 digest over the source (via the same `read_block` path as bulk copy, never holding the volume in memory) and carries it in `FinalizeComplete.volume_checksum` in a versioned, self-describing format (`"sha256:"` + 32 raw bytes, documented in the proto); the receiver re-computes the same digest over the destination after its final flush and sets `verified` accordingly. Fail-closed on every leg: digest mismatch ⇒ `verified=false` with a precise, content-free error ("destination digest mismatch: expected sha256:…, got sha256:…" — never volume data); unknown/unsupported digest format ⇒ `verified=false` naming the format (forward-compatible detection, no silent misinterpretation); unreadable destination ⇒ `verified=false`; and the sender treats `verified=false` as a migration failure — task → `Failed` with `Status::data_loss` (same integrity class as a chunk CRC mismatch), so `Completed` genuinely means "destination verified". Per-chunk CRC32, ack semantics, and the protocol are otherwise unchanged. Cost: one additional sequential full-volume read on each side at finalize. The new e2e leg corrupts the destination file out-of-band mid-migration (past every CRC check) and asserts the migration fails with the digest-mismatch error and the task ends `Failed`. (#392)
- **Storage (stord)**: the storage-migration acknowledgment protocol now works end-to-end — previously *no* migration could ever complete (issue #391, plus two further latent deadlocks found by the first end-to-end test; all pinned by the new `tests/migration_e2e.rs`). Four data-path fixes: (1) **round-ack deadlock** — the receiver only logged `RoundComplete` and sent nothing, so the sender blocked forever waiting for a round acknowledgment after the first dirty sync round; the receiver now always answers `RoundComplete` with an `Ack` carrying its highest processed sequence number, which both acknowledges the round and flushes its ack window. (2) **ack-window flush mismatch** — the receiver acknowledged only every 64 chunks with no final flush, so any phase whose chunk count was not a multiple of 64 (at 4 MiB blocks: any volume under 256 MiB) timed out after 30 s; the receiver now flushes outstanding acks at `FinalSync` and before `FinalizeAck`, the sender drains after `RoundComplete`/`FinalSync` instead of at a point the receiver can never observe (end of bulk copy), and the FinalizeAck wait tolerates in-flight boundary acks. (3) **Init handshake deadlock** — the sender awaited the stream response before sending `InitMigration`, but the tonic server handler blocks reading the first message before responding, so the stream could never start; the sender now queues `InitMigration` before opening the stream. (4) **gRPC message-size limit** — a 4 MiB `BlockChunk` plus protobuf overhead exceeds tonic's default 4 MiB decode limit, so the receiver rejected every real chunk with `OutOfRange`; both serving paths (mTLS TCP listener and Unix socket) now accept migration messages up to 8 MiB. Fail-closed semantics are unchanged: CRC mismatches still fail the migration, out-of-bounds chunks are still rejected, sparse-zero handling is untouched, and no mTLS path was weakened. The no-TLS `FailedPrecondition` also now cites the real config keys (`migration.client_cert_path`/`client_key_path`/`ca_cert_path`/`dest_server_name`) instead of the nonexistent `migration.tls.*` section. The new end-to-end test runs the real `MigrationSender` against the real receiver served by `serve_migration_tls` on a loopback mTLS listener with `LocalFileBackend` on both sides, covering: a small (2-chunk, sub-ack-interval) volume completing with byte-exact destination; dirty sync rounds transferring concurrently written blocks; and the `PausedFinalSync` pause handshake driven through a `MigrationTaskTable` entry. (#391)
- **Control plane (dev-mode operator contract)**: `CHV_ALLOW_INSECURE=1` on a production build fails with `InsecureModeLockedOut` telling the operator to "rebuild with: cargo build --features dev" — but `chv-controlplane` had no `dev` feature to enable (it existed only on the `chv-controlplane-service` dependency and was never forwarded), making the documented dev-build path impossible. The bin crate now forwards the feature (`dev = ["chv-controlplane-service/dev"]`), CI gained a compile guard (`cargo check -p chv-controlplane -p chv-agent --features dev`), and the dev path was verified to pass both security validators and proceed into bootstrap. (prompt-03 post-merge review)
- **Storage (stord)**: the migration receiver now listens on TCP with mandatory mTLS (issue #390). Previously only the *sender* half of migration TLS existed: a stord configured as a migration destination still never opened a TCP listener, so cross-node migrations could not connect — the destination served the migration service only on its local Unix socket. New all-or-nothing `[migration]` receiver fields (`listen_addr`, `server_cert_path`, `server_key_path`, `client_ca_path`) with fail-closed startup validation (partial config, unreadable files, mismatched keypair, invalid/empty client CA bundle, or a bad listen address is a startup error; no fields = source-only stord with no TCP listener). `migration.enabled` is the master switch for the receiver too: receiver fields set with `enabled = false` are a startup error rather than a silently ignored (or silently opened) listener. When configured, `StorageServer` additionally serves `StorageMigrationService` on a TLS TCP listener via tonic `ServerTlsConfig` with `client_ca_root` and *no* `client_auth_optional` — rustls rejects peers without a valid client certificate during the TLS handshake (loopback-tested: no-cert and untrusted-CA clients are rejected; valid-identity clients complete a gRPC round trip). The Unix-socket serving surface (both services, 0600 socket, group ownership) is unchanged and no mTLS path was weakened. (#390)
- **Storage (stord)**: wired the storage-migration mTLS path end-to-end (previously hard-coded `None`). Added a `[migration]` config section (`enabled` plus `client_cert_path`, `client_key_path`, `ca_cert_path`, `dest_server_name`) with fail-closed startup validation: missing fields, unreadable files, a malformed/empty CA bundle, or a mismatched keypair is a *startup error*; there is no plaintext fallback and no skip-verify option; PEM/key material is never logged. `chv-stord` now installs the rustls ring crypto provider and passes the validated `MigrationTlsConfig` into `StorageServer`. Example config documents file ownership, permission, and rotation expectations. (#232)

Defense-in-depth: the interceptor constructor returns the same typed error. (#233)
- **Architecture Designer dashboard logged users out on mount.** `getArchitectureDrift` accepted a placeholder `_fetch` parameter where a token argument should have been; the dashboard fan-out at `/architectures` called it without a token, the BFF returned 401, and the global `bffFetch` 401 handler redirected the user to `/login`.
